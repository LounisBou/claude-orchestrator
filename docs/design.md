# claude-orchestrator — design

This document describes the plugin as it is now: its parts, how they fit, and the design
decisions that still hold, each with its reason. It does not restate the rules. Where a
skill, a reference or a template states one, this document points at it, because a fact
kept in two places goes stale in one of them. How a decision was reached, and every
decision since reversed, is in the repository's history.

Sections 1 to 9 describe the architecture. From section 10 on, each section is a decision
that holds, under the number it has carried since it was taken: the scripts, the commands
and the test suite cite those numbers, and the suite checks that every number cited names a
section here. A number that is absent names a decision a skill now states in full.

## 1. Goal

One session supervises implementer sessions instead of writing code itself: it writes their
briefs, launches them, reviews every delivery on the artifact, rotates saturated agents and
hands over to a successor before its own judgment degrades. This plugin ships that method as skills, the tab tooling the method needs on macOS, the briefs as
templates, and a context gauge that does not depend on any particular status bar.

Everything here was extracted from a working setup: the skills were loose files in the
operator's configuration directory, the gauge was a patch inside an installed status-bar
script, and the briefs were rewritten by hand for every phase. The plugin makes them
installable, versioned and independent of that machine.

Four ideas carry the rest, each stated where it binds:

- **The operator's word comes first**, and it is answered: `skills/orchestrator/SKILL.md`,
  « The operator's word comes first, and it is answered » (section 47 here).
- **The orchestrator orchestrates and never implements**, and it launches, verifies,
  terminates and replaces its agents itself: `skills/orchestrator/SKILL.md`, « Overview »,
  and `skills/orchestrator/references/lifecycle.md`.
- **Measured, never estimated**: a context figure comes from the gauge
  (`hooks/gauge.ts`'s measure file, written on every gauge pass), a verdict from the
  artifact (`skills/orchestrator/references/review.md`).
- **A rule lives once, and a decision that changes changes its directives in the same
  move**: `skills/orchestrator/references/briefs.md`, « When a decision changes, the directives
  change in the same move » (section 18).

Out of scope: Windows and Linux terminal automation (the iterm-agents skill is macOS only;
the other skills and the gauge work anywhere the host runs); and editing the user's status
line script — the module needs nothing there, and install only unwraps a tap a previous
release left in front of it.

## 3. Context gauge

The hooks module measures every session itself, in-process: `hooks/gauge.ts` answers the host's own measure events and `hooks/gauge-core.ts` holds the rules, pure. What follows is why it is built this way. The shell pipeline it replaced — a tap wrapped around the operator's status line, a `ctx/` file per render, a gauge script that fell back to scanning the transcript — is gone; the one file that survives is the measure file, because external processes cannot read the module's memory.

### 3.1 The host is asked, not inferred from

The host fires a measure event after each turn and on each change of a plan-limit percentage, and the reading it carries — tokens, window, percent, model — is the figure itself, not an inference from a payload meant for a status line or from the transcript's last usage block. Both earlier tiers paid for their indirection daily: the tap forced a cohabitation protocol with whatever status bar the operator ran, and the transcript scan paid a process spawn to approximate a number the host already knew. The module writes no marker files and keeps its once-per-session and once-per-drift state in memory; a reload of the module resets it, which is the correct reset, because a reloaded module has measured nothing yet. A /clear and a compaction of the main conversation drop the figures measured before them too — the band, the store's row and the measure file stop showing them — since they are no longer the conversation's; the next answer measures again.

### 3.2 The measure file

`<state root>/measure/<session-id>.json`, one line: `context_tokens`, `context_window`, `context_percent`, `model`, `updated_at`. It is rewritten on every measure and removed on session end, and it is the only channel any external process is documented to read: the shared store it feeds — `store/sessions/`, one file per live session, written on each measure beside this file, removed on session end, kept while the session's host process lives — the row carries its pid, so a session idle for hours keeps its row and one that ended without the end event (a crash, a kill) loses it the moment its pid is gone; a row written before rows carried a pid is read as no row after an hour without a measure — is a file tree an outside process could open as well, but none is given it: the store feeds the module's own surfaces alone (the three commands), and the plugin's one documented external reader, the launcher's `--inherit-model`, reads this file's `model` (section 27). The module's write is not atomic, so every reader treats an unparseable or empty line as unmeasured; the next turn rewrites it. `install.sh` creates the directory and prunes a file only past a week and when no live session owns it (the host's registry names each live session's id), so ended sessions do not accumulate and an idle one keeps the file it will read again.

### 3.3 The band

On each measure the module draws one band above the prompt — the fill, the token count, the rotation marker, warning past the gate — through the host's render call, after checking what the session's surfaces can draw. Where nothing draws, a chat panel or a headless run, the band is skipped and nothing is lost: the same figures answer `/orchestrator:status` and the gate's own lines still speak. One invalidation per measure, far under the host's bound.

### 3.4 Install and uninstall

`install.sh` refuses a host older than 2.1.287 (the hooks module needs the events and the API it binds), unwraps any tap a previous install left in front of the operator's status line — keeping the command that followed the tap as written, the saved object only filling keys the line lacks, or coming back whole when the tap was all the line held — creates `measure/`, removes `ctx/`, prunes a measure file only past a week and when no live session owns it, and removes the tap's copy, its saved object and the old gates' logs once no line runs the tap; `uninstall.sh` runs the same unwrap (it sources `install.sh`) and removes the state directory whole, keeping only the tap's copy and saved object while a line it cannot read may still run the tap. The steps, the backup and the idempotence are the two commands' own (`commands/install.md`, `commands/uninstall.md`); why the comparison reads the home's spelling is section 33.

Requirements: `jq` for the installer and the workflow scripts, `python3` for the tab tooling's environment, bash 3.2 for every shell script.

### 3.5 The context gate

The module's context gate (`hooks/guards.ts`, on every prompt submitted) speaks only to orchestration sessions: those whose name, given at launch (`--name`) or by a rename, starts with `Orch :`, `Agent :`, `Audit :` or `Coord :`. The name is read by the module's own name walk (`hooks/session-name.ts`, the reading the stop gate and the store share), in-process, so no interpreter is started per prompt. It finds the session's own tty, then the host process on it — a pid the host keeps a record for (`<config dir>/sessions/<pid>.json`), else a process whose command is the host's binary — and takes, in this order: the record's `name`, its surrounding straight or curly quotes stripped; else the process's launch `--name`; else, only when the host keeps no record for that process, the last `custom-title` in the transcript's tail (its last 2 MiB, never the whole file). The process read is the session's own: where the host keeps records, only the one whose record carries this session's id (`$.session.id()`) counts, else the first record that carries no id at all (a host that writes none), never a record carrying another session's id. A session launched underneath another, such as a headless run started from its shell, has no tty and climbs to its parent's, finds no record of its own there and speaks for no one: no name and no role, so no notice and no gate report, and its store row carries no name and no role, never another session's. A walk that fails or does not finish in its bound is an unknown name, never a session found unnamed: a name already known is kept. A name the launcher knows exists and cannot read, and any failure of the reading itself, are appended as one line to the module's log (section 4.4), so a session that went dark leaves a trace; a session with no name at all is the normal case and is not logged. A session with no role name — one the operator started by hand and never renamed, or one whose name cannot be read — gets no gate line and no « unmeasured » line; the model-drift line alone reaches every session (section 32). At or past the gate — 300,000 tokens (30 %) on a window of 1,000,000 tokens or more, the common case, and 80 % of a smaller window (`ORCHESTRATOR_CONTEXT_GATE`, `ORCHESTRATOR_CONTEXT_GATE_TOKENS`, `ORCHESTRATOR_LARGE_WINDOW`; the launcher sets the token gate for one session with `--gate-tokens`, see section 60) — it puts one line in front of the session, fitted to its role: an orchestrator succeeds at the next quiet boundary, an agent finishes its unit, reports its measured context and stops, an auditor writes its one report and stops or, with work the operator gave it after the report still in hand, succeeds, the coordinator succeeds when no relay is in flight. Below it, it prints nothing; unable to measure, it says so once per session instead of staying silent as if the fill were low — the first prompt of a session, before any measure exists, stays silent, because nothing has been measured yet and that is not a fault. It exists because the rule « succession is yours to trigger » lived in the skill and was not applied: a sentence the model must remember can be rationalised away, a line the harness puts in front of every prompt cannot. It also carries, once per change and in every session whatever its role, the line the gauge wrote when the model answering the session changed under it (section 32). The thresholds it enforces are the rulebook's: `skills/orchestrator/SKILL.md`, « Thresholds ».

### 4.3 Hooks

`hooks/hooks.json` declares one hooks module and nothing else; every gate below is enforced in-process by the host rather than remembered by the model. The context gate is section 3.5; like the stop gate it reads the session's name before anything else, and leaves every session outside the orchestration alone. The push guard (`hooks/guards.ts` on the Bash tool, `hooks/tokenizer.ts` reading the line the way the shell reads it) runs in a session the launcher spawned — the launch marks it, and a session the operator starts by hand is never touched — and refuses a force push other than a rebase's `--force-with-lease=<branch>:<sha read>`, the one force the review rules allow (`skills/orchestrator/references/review.md`, « Review on evidence »). It reads text, so a push hidden inside a string another program runs passes; the tokeniser's fixtures say which shapes it cannot see. The push guard's own failure — a re-entered call, or one past its time bound — is decided on the launcher's mark as last read: closed in a spawned session, which is denied with the reason, open in one the operator started, and a forced push refused while the mark was never read. The stop gate (`hooks/guards.ts` over `hooks/stop-gate.ts`, on the Stop event) runs when an orchestrator's session ends a turn — its name, read by the name walk of section 3.5, starts with `Orch :`, decided from the session's own tty before any call to the launcher's listing; every other session is left alone — and refuses the stop at most once per turn. Its first check, what will wake the orchestrator, reads the message's last line first, normalised of its markup, dash and spacing. A last line `handed over` lets the stop pass: the predecessor of a succession is done. A session that has handed over — it ran the launcher's `spawn --successor` through Bash in its main thread and the call succeeded, or the module accepted its `end_session` — passes on `waiting: done`, its agents and rows now the successor's. A question declared blocking (`waiting: operator — blocks: <what it blocks>`) passes, and is logged, before any refusal below: an idle agent may be waiting on the very answer the block names. Then the gate refuses while an agent of its own chain is idle and its pull request is open or merged (« stand it down now — or, if it waits on a question you have not answered, answer it », whatever another agent is doing; the pull request is found from the agent's tty, its process's working directory, that checkout's branch and one `gh pr view <branch> --json number,state` run in that checkout per idle agent, none for a busy one, a failed or late read counting as no pull request). Otherwise the stop passes on a busy agent of its own chain, or, with no agent busy, on a `ci-watch.sh` this session started and still running, whose exit wakes it, or on a peer's idle notice it subscribed to (`SendMessage` with `notify_when_idle: true`, sent by its main thread) that has not arrived — the peer's notice or message ends the wait, and two hours end it regardless — and a session that has handed over is never told that nothing will wake it: on each side of a succession, the other's message will (an agent spawned with `--resident`, idle by design while a background command of its own waits, is never counted as an agent of the chain and lifts no other check, but where nothing else would wake the orchestrator its background command will, so it lets that stop pass). `waiting: done` passes only with no checkout of the project, no agent of its own, no open row in the dispatch records the session registered (`dispatch-record.sh` registers its record on every command, `summary` lists the open rows), and every goal of the `goals.md` beside them met or ruled out (section 64). Idle agents with nothing declared, a malformed machine line, a bare question and nothing that will wake it each refuse with their own line. When the stop passes that check, the second reads the real CI state from what `ci-watch.sh` already watched, with no network call at the stop: its logs under the state directory's `ci-watch/`, one per pull request (`<slug>-pr<n>.log`), each with its owner file (`<slug>-pr<n>.log.session`, the id of the session that armed the watch), kept when the owner file names this session; a log with no owner file, or an owner file that cannot be read, is no session's and is not read. Before the owner file, the gate kept every log of the session's repository or `here`, and on geonative-api a failing `here` watch armed in one checkout stopped three sessions that never held it. A log carries no head sha, so a watch is told once by its log's first line, hashed — a new watch truncates its log and starts a new first line, and the telling starts over; the log's modification time, which every snapshot moved, once refused the same failing set at every stop. Pending checks refuse once, then pass until a check fails; failing checks refuse once per failing set; a log whose checks have all finished green is recorded done and passes. A pending pull request with a `ci-watch.sh <n>` process alive is waited for, neither told nor recorded (one `ps` read for both checks); the refusal otherwise arms that watch in the background, `ci-watch.sh <n>` with `run_in_background` (section 62). A check listed for the repository in the state directory's `ignored-checks` file (`<owner>/<repo> <check name>`, one per line) is not read, for a job that fails by design; a log carries no draft flag, so a draft guard is not recognised at the stop and `ignored-checks` is its fallback while the pull request is a draft (`ci-watch.sh` itself classifies draft guards, section 62). When the stop passes, the gate runs `workspace.sh sweep` within what is left of its deadline, at most once per ten minutes. It reads facts, never the words of the message beyond its last line; its own failures let the stop pass and are logged. Its original spec is `docs/specs/2026-10-01-stop-gate-design.md`, superseded where this section differs.

### 4.4 The state directory

`${CLAUDE_CONFIG_DIR:-~/.claude}/claude-orchestrator/` holds what the plugin keeps between sessions: `models.json`, the operator's tier map (section 10); `mcp.json`, the operator's server catalogue (section 42); `chains/`, one chain file per orchestrator tty (sections 21, 26, 34); `prompts/`, the files each launch was made from (section 45); `measure/`, one measure file per session (section 3.2); `hooks-module.log`, the module's own log — one line per stop the stop gate refused, per `blocks:` stop, per failure of a handler's own, per sweep deletion, and per session of the orchestration whose name a gate could not read, every session on the machine writing to it at once: each line is appended by `hooks/log-append.sh`, one append-mode write that never interleaves with another's and never rewrites the file, so no session's line is lost, and past 2 MiB the log is moved to `hooks-module.log.1`, the one previous generation kept, under a directory lock, rather than wiped; the stop gate's heads record, its `ignored-checks` list and its sweep stamp (section 4.3); the store (section 2, the `hooks/supervision.ts` row); `records/`, per host session, the dispatch records it touched, which the stop gate reads for open rows; and the tab tooling's Python environment (section 14). `ORCHESTRATOR_STATE_DIR` overrides this path, and the sharing follows the root: the stop gate's whole state root resolves the override first, else the config dir's `claude-orchestrator`, because everything hanging off that root — the chain files, the records registry, ci-watch's logs, the heads record, the `ignored-checks` list, the sweep stamp — is what the surviving shell scripts still share, and `dispatch-record.sh`, `ci-watch.sh` and the launcher build the same root from the same override; the registry the progress command reads resolves it the same way. The module's own artifacts — the measure file, the store, `hooks-module.log` — stay under the config dir whatever the override says: no surviving script shares them, and an override aimed at the gates' shared root does not move them. `install.sh` and `uninstall.sh` build the state directory from the host configuration directory directly and do not read that override. Three things live elsewhere on purpose: the trust record is the host's own file (section 31), the dispatch record lives with the project being built (section 13), and the checkouts live under the workspace root (section 30).

## 5. Templates

No date or hour is written from memory (`skills/orchestrator/SKILL.md`, « Carried at every step »): a brief is a file named by its subject, the coordinator's succession brief is the one `succession-brief.md` its successor overwrites, and a time a record must carry is a command's output. Six briefs with `{{PLACEHOLDER}}` markers, each carrying the sections the orchestrator skill makes mandatory: `agent-phase-brief.md` (one implementer, one phase, one pull request), `agent-rotation-brief.md` (a fresh implementer resuming a phase), `agent-review-brief.md` (one review round, read-only, readers sized by the orchestrator), `agent-comments-brief.md` (one pass over a pull request's open threads), `agent-audit-brief.md` (one audit of the method, one report, then stop or, with work the operator gave it after the report still in hand, succeed) and `orchestrator-succession-brief.md` (a successor taking the orchestration over). How a brief is built from them is `skills/orchestrator/references/briefs.md`, « Agent prompt recipe ».

A template is read by an agent that does not load the orchestrator skill, so it keeps in full the rules that agent needs — the orchestrator's address, the STOP-and-ask clause, synchronous commands, the measured context as it nears the gate — and the skill points at the template rather than restating them. No template points at a plugin path, and none carries a host variable or a session reference (section 11): `brief-lint.sh` flags a brief that does.

## 6. Commands

Each command carries its own procedure and points at the skill for the rules. `install` and `uninstall` unwire any tap a previous install left and keep the state directory (section 3.4); `status` lists live sessions with their measured context fill, `agents` reports each running implementer's progress and `progress` says where the build stands — the three answered without a model turn by the module's command handlers, their markdown files kept as the degraded path; `decide` runs the decision round, one arbitration at a time; `succeed` runs the orchestrator's succession (section 9.3); `audit` launches an audit of the method on the operator's word (section 52); `coordinator` and `coordinator-end` start and end the machine's coordinator on the operator's word, and `sleeping` lists the orchestrators it paused and drops one (section 9.5).

A command names in its `allowed-tools` the tools it needs, and nothing more: `progress` lets the artifacts win where they disagree with the state file, and corrects the file before presenting, which is why it holds `Edit` (section 56).

A skill never takes a command's name: a plugin's commands and skills share one namespace, and a skill named like a command would shadow one or the other. The audit is a command and its brief, not a skill.

## 7. Tests

`tests/run-tests.sh`, bash, no network, no terminal automation, an isolated `HOME` per case: the installer, every script's refusals and dry runs, the surviving hooks' prose, the prose the directives must carry, and the repository's policy: the prose contains no vendor or product name outside the load-bearing identifiers, no model family name anywhere and nothing machine- or project-specific, and the guard proves it can still SEE a violation, through a probe planted and removed by the same function, because it once masked every hit behind the repository's own path. The suite also holds this document: the layout block against the tracked files (section 2), every section number the code cites against the headings here, and every relative link in `README.md`, `docs/`, `skills/` (skills and their references), `commands/` and `templates/` against the file and the heading it names — `evals/` is not read.

`tests/e2e.sh` plays one real round against a live terminal and stays out of the default suite on purpose (section 15).

`evals/` is the behaviour suite, run by the host's plugin evaluation command: a small core of cases, each one that has caught a real defect or guards an irreversible action, graded on the decision, compared case by case with a committed baseline. How a case is staged, run and read is `evals/README.md`; which rules the cases cover and why is `evals/SELECTION.md`.

`ORCHESTRATOR_*` variables are the suite's door into every script (a dry run, a state directory, a fixture process table) and the operator's alike (section 45).

## 8. Release

Version in `plugin.json` AND in both fields of `marketplace.json` — the same fact in three places, so the suite checks they agree and that the number never falls BEHIND a published tag (equal is a tagged release, ahead is unreleased work; only behind is the defect). Tag `orchestrator--v<version>` pushed with the code — the prefix since the plugin was renamed; the first three releases used `claude-orchestrator--v`, and the suite reads both when it checks the version against what is published. Install:

```

/plugin install orchestrator@lounisbou

```

The marketplace is the operator's family one, `lounisbou`, where every plugin of the family is listed; this repository's own `marketplace.json` stays the single-plugin manifest the suite reads for the version, as every plugin of the family carries one. ## 9. How the parts fit

### 9.1 A session's life, from launch to close

The orchestrator's core loop — plan, brief, launch, verify, review, terminate, replace — is `skills/orchestrator/SKILL.md`, « The core loop », each step naming the reference to read at the moment of the action.

- **Plan.** A validated spec and a phase plan with exact contracts, one kind of change per phase, one agent and one draft pull request per phase stacked on the previous branch head: `skills/orchestrator/references/briefs.md`, « Prerequisites and phase rules ».
- **Brief.** Written from a template to a path the fresh session can open, carrying its tier and the reading that chose it (`orchestrator:model-routing`, section 10): `references/briefs.md`.
- **Launch.** `workspace.sh create` makes the phase's checkout (section 30); `iterm-agent.sh spawn --brief` lints the brief, builds the one-line startup prompt and opens the tab beside the orchestrator's, at the tier the brief names, with the servers chosen for the agent, in a checkout the host trusts (sections 12, 21, 31, 42): `references/lifecycle.md`, « The agents' lifecycle is yours », and `skills/iterm-agents/SKILL.md`, « Safety order for a launch ».
- **Verify.** The launcher waits for the host CLI on the tty and reads the mode the session came up in (section 43); the orchestrator reads the tab, the process and the listing, then relies on the module's reports: the agent's status line, its gate crossing, and a turn ended without a status line.
- **Control.** An agent reports its measured context as it nears the gate, and the number is read against it: `SKILL.md`, « Carried at every step » and « Thresholds ».
- **Terminate.** An implementer is stood down at the verification of its delivery (section 45), its tab closed by tty and proved gone on the process table (section 46), its checkout deleted: `references/lifecycle.md`, step 4, and `skills/iterm-agents/SKILL.md`, « Tab hygiene ».

### 9.2 The review round

One review session per round, spawned from `agent-review-brief.md` in a copy pinned at the head under review (section 37), its readers sized by the orchestrator, from its own reading to several lenses, the project's own norms tool among them, and reporting once. The orchestrator verifies every finding on the artifact, keeps only what must necessarily be fixed and names every dropped item with its reason, dispatches one correction round, and verifies it itself. The round lands on the dispatch record, and `ready` refuses a head no round read (sections 55, 58). The rules are `skills/orchestrator/references/review.md` and `SKILL.md`, « Thresholds »; review comments on a pull request go to a comments session, `references/review.md`, « Review rounds run in disposable sessions ».

A pull request stays in draft. Ready, from the orchestrator's side, is implemented, reviewed, corrected, verified, `ready` green and rebased; then it tells the operator « ready ». Merging a pull request and taking it out of draft are the operator's, on his clear and explicit request, and in no list of what the orchestrator decides and moves on (sections 23, 58).

### 9.3 Rotation and succession

An agent at the context gate is replaced: `rotate` spawns the fresh session from a resume brief (`agent-rotation-brief.md`) and verifies it before it closes the old tab, which stood down first (section 19): `references/lifecycle.md`, « Context rotation ». The orchestrator at its own gate hands over: `commands/succeed.md` checks that the standing succession brief (`orchestrator-succession-brief.md`) exists and instantiates it when absent, lints it, and spawns the successor with `--successor` (it takes the predecessor's place, name and chain, section 34 and 39) and `--inherit-model` (the model in use now, section 27); the successor verifies the state on the artifacts, re-announces its address to every agent, confirms the takeover, and closes the predecessor's tab on its « handed over » (section 45) — one the launcher did not open included, which ends its own session through the module's `end_session` where the host refuses the close, the end proved on its tty: `references/lifecycle.md`, « Your own context (the orchestrator is not exempt) ». The operator's duties travel in the succession brief (section 47). At takeover the successor reads the rulebook and its brief's live state, the rest by section on demand: its predecessor writes the live part of the state file into the brief's « Live state » section (rows open, pull requests open, agents running, the rulings still binding, the next step) and the lint holds the whole brief to 10,000 characters. Measured on transcripts, as the input and cache tokens of each assistant turn, a successor confirmed its takeover at about 75k to 97k tokens against a gate of 300k, of which 45k to 65k is the host's own before any tool; the part this plugin decides was the reading list, which ordered the spec, plan, runbook, state file and briefs directory read whole. The successor's announcement now carries its measured `context_tokens`, so the cost of each takeover is a figure. The successor's reading is the one the module records when the turn that sends « takeover confirmed » ends, read at its next turn's first tool call — the module writes the measure file only when a turn ends, so no reading inside that turn is that turn's — and it reports that one rather than any later one, so that its figures compare from one succession to the next: taken after the predecessor's close and whatever the successor read meanwhile, one orchestration's takeovers measured 81k, 88k and 104k at different turns. It reports two figures, its first turn and the turn that sends « takeover confirmed » (each recorded when that turn ends), because the gap between them is what the takeover's verification costs.

### 9.4 The audit

An auditor weighs the method's cost against its yield and proposes to the operator, who launched it; it writes one report and stops: section 52. Kept on by the operator past its report, it succeeds at its gate instead, like the coordinator below: `templates/auditor-succession-brief.md`, `spawn --successor` from an `Audit :` session.

### 9.5 The coordinator

The operator runs several orchestrations on one machine at times, and they can step on each other: two checkouts on one branch, two agents pushing to it, two suites at once, one orchestration moving onto another's pull request. A coordinator, started with `commands/coordinator.md` and ended with `commands/coordinator-end.md` on his word only, watches for that from the outside. It reads the facts now — `skills/coordinator/scripts/coordinator.sh`, `facts` and `owners` (its header is the contract) — rather than any declaration: a pull request is traced to its orchestrator along its branch, the checkout on it, the session working there and the address that session's brief names. At its start it tells every orchestrator it exists, that every question for the operator now goes through it, and that it may be asked the facts, and asks each once to confirm the pull requests the facts give it; at every later turn it already acts on, it re-reads that same listing and sends the same message to whichever `Orch :` session is missing from its notes' announced list — a successor of one already announced counts as missing too — so an orchestration started after it still learns of it, with no wake-up scheduled to check for one. It is the operator's single question interface, on his order: each question an orchestrator has for him — its own arbitrations, its agents' questions it relays — goes to the coordinator, carried by the hooks module rather than by the orchestrator (below), which relays it verbatim with its sender's name, one at a time, sends his answer back verbatim and dated, and never answers one itself. By default, on his later order, it runs every relayed question through the whole decision round of `commands/decide.md`, without his typing the command: a round file in its scratch directory is the ledger — every question received is written there first, with its sender, the time received and its status, and the round ends on « The round is complete: N/N » — so none is lost; the questions come grouped by the orchestrator that sent them, each group opened with that orchestrator's own three-to-five-sentence account of what it works on, and every question names its sender and the coordinator relaying it, since he runs several coordinators. A successor takes the open round file over through its brief; with no coordinator running, the orchestrator asks him directly. It answers questions from the facts, flags a collision to both sides, relays to the operator what is his (a merge, a scope, a method, ending a process), carries his orders to all, and gates nothing: `skills/coordination/SKILL.md` (named `coordination`, not `coordinator`, so the skill never shares its start command's name — section 6). Its succession at its context gate is the same skill's « Your context », with `templates/coordinator-succession-brief.md`: the successor closes its predecessor, the first coordinator started by hand included, and that one ends its own session through the module's `end_session` where the host refuses the close. The launcher refuses to move or rotate the coordinator's tab without `--force`, knowing it by its `Coord :` name or by the coordinator's record placing it on that tty.

The relay is the hooks module's, at the end of an orchestrator's turn (`hooks/relay.ts`, wired in `hooks/supervision.ts` on `turn.complete`, which fires once the turn is over — a stop the gate refuses goes on in the same turn, so `classic.Stop`'s message is not always the last word): the answer's last line, read with the stop gate's own machine-line regex, is written to the session's wait file beside its store row (`store/waits/<id>`, renamed into place, its one writer the relay, so the measure's merge of the row can never put an older wait back) — `waiting` (`operator` or `done`), `blocks`, `waiting_since`, kept while the same wait lasts and cleared when a turn starts or ends without it — which the supervision pane and `/orchestrator:status` merge into the row and `coordinator.sh facts` (its `waiting` lines) reads. Once per wait, the registered coordinator (`<state>/coordinator.json`) is sent one `[module]` message through the engine's session send: the header « <name> waits for the operator since <UTC> — blocks: <x> », the line « reply with SendMessage to: <name> » and the question as the answer carried it, cut at 4,000 characters and said; or « <name> reports its work done and proposes to be closed ». The same wait — same blocks, same question — is never sent twice (its fingerprint kept in the wait file once delivered); a new question is. When the operator types a prompt (composer or bridge) in an orchestrator whose relayed question is still on him (`withdrawOnTyped`, on `prompt.submit`, which runs before `turn.start`), the coordinator is sent one `[module]` message — « <name> withdraws its question for the operator since <UTC> — blocks: <x> » and « the operator answered it in <name>'s own tab: nothing to send back » — and the fingerprint is forgotten once it is delivered, so the same question asked again is relayed again; a refused send is one log line, tried again at the next typed prompt, and a slash command, any other prompt kind, role or state sends nothing. No coordinator registered, a session that is no orchestrator, a subagent's or an interrupted turn: nothing is sent. A send refused or late is one log line, never a held turn. The defect it ends: an orchestrator that asked the operator in its own tab looked stopped from outside, and the coordinator spent two full turns asking it why; the model now writes nothing for the relay.

The coordinator is found on this machine first (`<state>/coordinator.json`), else from the last peer message whose envelope names a `Coord :` sender (`store/coordinator-learnt`, its `from` address and name), so an orchestrator on another machine reports too. Its store row follows the same way, silently (`hooks/remote-row.ts`): one `[module-row] {json}` line sent by the module when the wait, the repository or the pull requests in flight, or a 5 % band of the fill changes, or 10 minutes passed, never on a repeat; the row carries the store row's repository and the pull requests its watches cover (`prsInFlight`: each `<slug>-pr<n>.log` of the state dir's `ci-watch/` whose owner file names the session, unless its `-base` log says it merged; `here` takes the repository, and a slug is read as `owner_name` at its first underscore). The coordinator's `session.receive` hook consumes the line before any model reads it, checks it against a strict schema (the twelve fields, or the ten of 0.58 and 0.59 read as no repository and no pull request) and writes it to `store/remote/<name>`; the pane and `/orchestrator:status` draw it as `remote <machine>`, a live local row of the same name winning, for 24 hours after its last reading — it carries no pid, and an orchestrator waiting on the operator takes no turn to refresh it. `coordinator.sh facts` and `owners` read the same store: a `remote` line per kept row, a remote row's pull request counted as one more orchestrator in a `collision pr`, and named as the orchestrator of an « unknown » pull request in `owners`, with « not read on the forge here » where the repository is not read on this machine.

On the operator's word only — one orchestrator, several or all — the coordinator pauses orchestrations and wakes them: his order of 2026-10-13. It asks each to prepare its succession for a pause; the orchestrator reaches a quiet boundary (its agents stood down, its CI watches stopped, its state current), writes and lints its standing succession brief as `/orchestrator:succeed` does, and replies `paused-ready` with the brief, its model and its effort, spawning no successor and closing nothing of its own (its bullet in `skills/orchestrator/references/lifecycle.md`). The coordinator closes its tab as a successor closes a predecessor — the title guard, `end_session` where the host refuses — and records it sleeping through `coordinator.sh sleep`, under the registration's lock, in `<state>/sleeping.json`: its name, brief, directory, model, effort, the time it slept, its pull requests and checkouts. The record lives apart from the coordinator's own, so it survives the coordinator's succession and its end. A sleeping orchestrator is not missing: `owners` attributes its pull requests to it, « sleeping since », and no announcement chases it. On his word to wake, the coordinator spawns it with the launcher's `--wake` — its recorded name, model and effort, right of the coordinator's tab, in no chain, under remote control — on its brief, whose takeover handshake the startup prompt voids, its predecessor being gone; `wake-done` removes the record once the spawn is verified. `/orchestrator:sleeping` lists them, answered by the module; `drop <name>` abandons one after one confirmation, the record removed and the brief moved to `abandoned/` beside it, its pull requests, branches and checkouts left to him. A pause refused or failing reaches him through the coordinator's round, and that orchestrator is not closed.

On his word as well, an orchestrator is moved from one machine to another: his order of 2026-10-16. It is asleep on the first and woken on the second, by the coordinator's section « Moving an orchestrator » in `skills/coordination/SKILL.md` and the orchestrator's bullet beside the pause's. A move is carried by marked messages, like the remote rows above, consumed by the hooks module (`hooks/moving.ts`, the protocol pure in `hooks/move.ts`) before any model reads them; the sender calls `move_send`, which refuses the move, nothing sent, unless every checkout the record lists is clean and pushed. The sender announces a manifest — the record (name, brief, directory, model, effort, pull requests, checkouts, the directory's remote and branch, the operator's order), the origin's home and configuration directory, and for each file its size, its sha256 and its chunk count — then sends the chunks, then « sent ». The receiver's module keeps what arrives under the store, joins a file once all its chunks are in, checks its hash, rewrites the origin's paths into its own, writes it in its briefs directory and acknowledges it, file by file; it asks again, with `missing`, for the chunks it lacks, at most `MOVE_MISSING_ROUNDS` answers per move, and ends with `done`. The sender keeps the address pinned at the first answer it matched by name, and drops any later answer from another. No timer runs: the same call repeated is the same move and resumes it. Only two texts reach a model, both written by the module: the arrival notice on the receiver, which carries the facts, the order verbatim and the launcher's opening, and the notice of the outcome on the sender, acknowledged or failed — the only text a model reads of a move. Code never travels this way, it goes by git; the receiver opens an arrival only on the order the coordinator relayed for that name (the coordination skill's « Moving an orchestrator » in `skills/coordination/SKILL.md`), which a manifest cannot supply.

On his word to open a new orchestration, the coordinator opens it, and never answers that he should do it himself: his order of 2026-10-15. A remote orchestrator asked to launch one tried a free title and a remote-control command in the new tab, and the host's own review refused even the dry run as an autonomous agent launched at another session's request. The coordinator here had opened two that morning by bending `--wake`, which is for a sleeping orchestrator. The launcher's `--open` is that opening: a title `Orch : <subject>`, right of the caller, in no chain, under remote control, on the deep tier unless told. It is refused when the caller's session reads neither `Coord :` nor `Orch :`, so an agent never opens an orchestrator. On another machine the coordinator relays the order verbatim and dated to an orchestrator there, which runs the same command (`skills/orchestrator/references/lifecycle.md`). The host's review is lifted by a standing rule, on his ruling of 2026-10-16 that the opening is always allowed, for every session: every `install.sh` run writes one rule in the user-level `settings.json`, `Bash(<installed plugin>/skills/iterm-agents/scripts/iterm-agent.sh spawn --open *)`. It names the launcher by its installed path with nothing before it, so another script of that name, a launch with its environment changed or chained to other commands, and any other spawn still go to that review. A first draft of the rule began with a wildcard, and its review found it matched any command line that merely contained the words. The installer writes the rule by default (`--allow-open` stays accepted and changes nothing, earlier instructions still name it), a refusal on another machine ends once the plugin there is updated and its `install.sh` run, and it moves a rule granted an earlier version to the new path at each install, its reach unchanged. The caller check reads the real process table, and refuses the suite's two stand-ins outside a dry run: it stops an agent's mistake, while the rule's exact form keeps a session set on deceiving it in front of the host's review. No session is asked to edit its own permissions: the host refuses that too, and rightly.

It lives outside the orchestrator on purpose. The orchestrator's skill carries one rule for it — ask the operator's question in the tab and end the turn on the machine line — and nothing else, so an orchestration run without a coordinator asks him directly, and one run with a coordinator loses nothing if it never asks it the facts. An earlier design put the orchestrators on a single channel through it, declaring before every dispatch and waiting for its « go »; that made every orchestrator carry the coordinator's weight to let it read what the process table, the checkouts and the forge already show.

## Decisions that hold

## 10. Tiers name capability, and the binding is the operator's

The plugin carries no model. Three tiers name capability — `deep`, `standard`, `light` — and what each runs on is bound in the operator's `<state dir>/models.json`, overridable per run by `ORCHESTRATOR_TIER_DEEP` and its two siblings; with a tier unbound, the launcher types no model argument and the host applies its own default. Every session the orchestrator dispatched ran at whatever the launcher hardcoded before the tiers existed, which put a model identifier in a plugin whose rules forbid one and paid the top tier for work a test suite already judges. How the orchestrator chooses a tier is `skills/model-routing/SKILL.md`, a decision aid to its own judgment; how a tier is bound is section 57. The briefs carry the tier down to each session, so an agent can say when the work outgrew what its brief assumed.

## 11. What a brief can carry

Three defects came out of running one phase end to end on a live machine, none reachable from the test suite, because all three live in what happens when a fresh session opens the file. Each became a rule of the briefs (`skills/orchestrator/references/briefs.md`): a path only the host can expand does not resolve in a spawned session's shell, so a brief carries absolute paths; a brief points at a policy and cannot grant one, since a file written by a peer is not the agent's user speaking; and nothing that reads as a second address goes near the one that matters, so the suite refuses a session-reference shape under `templates/`, as it refuses a host variable there.

## 12. Linting the brief

Specification is the largest category of multi-agent failure in the published taxonomy, and a brief is this plugin's whole specification act; nothing read the file before it reached a session. `brief-lint.sh` reads what a script can read, every finding a fault that has reached a live agent at least once, and `iterm-agent.sh spawn --brief` runs it before any tab exists; a finding no longer refuses the spawn, it prints on stderr as a warning and the launch goes on, the startup prompt built either way, so a brief spawned with `--brief` cannot skip the lint (`skills/orchestrator/references/briefs.md`, « Agent prompt recipe »). `--prompt` and `--prompt-file` reach no lint of their own; the script is run by hand first when a brief is worth writing anyway (`skills/orchestrator/references/briefs.md`, « Agent prompt recipe »). Its limits are stated where it is run: scope, contracts and tier stay the orchestrator's, because a guard whose limits are unstated is one people trust past them. `--expect-created <path>` exempts exactly the paths a brief dictates for the agent to create — chosen over accepting any path whose parent directory exists, which would have exempted every misspelt file in an existing directory.

## 13. Measuring what the routing rule assumes

The routing skill reverts a tier drop that cost a second corrective round. Nothing measured that, so it could only be applied from memory — and a rule applied from memory always finds the drop was free, because its cost lands rounds later where nobody attributes it. `dispatch-record.sh` keeps one row per dispatch as JSON lines — class, tier, rounds, verdict — and `summary` prints the signals the routing skill acts on (`skills/model-routing/SKILL.md`, « The record »): a drop that did not pay, a cascade that stopped paying, an escaped defect that arms a second reader. The row is rewritten in place rather than appended per event: a record of events would make every read a reduction over history, and the history is not the fact. The same row carries the readiness gate (sections 55, 58). `summary <record> --open` prints only the open rows, which is all a successor needs at takeover; the statistics stay on the plain `summary`, read when a dispatch is routed.

## 14. The terminal tooling speaks the app's own API

Every expensive launch bug this plugin carried came from one decision: the command was TYPED into a fresh shell. Typed, it could be truncated past a few hundred characters while the script reported success, lose its first keystroke to a startup question, and die on a non-ASCII byte; and placement drove a menu that needed an Accessibility grant and a focus flicker per move. The launch is now handed to the app's API with the tab's index (`skills/iterm-agents/references/commands.md`, « How the launcher builds a tab »). The surface is unchanged — same subcommands, options, messages and exit codes — across implementations, because skills, commands and briefs call it by those. `iterm-agent.sh` resolves an interpreter and hands over to `iterm_agent.py`, and the app's module is imported only by the subcommands that talk to it, so reading the tier map or a tty works on a machine with no environment and no window server. The environment is a virtual environment the installer builds under the state directory, because recent macOS refuses to install into a package-managed interpreter and a plugin has no business writing into one it did not create.

The suite holds the launcher by checks that read what the launch SAYS. A guard that reads an implementation is green on the day the implementation changes shape and wrong the day after.

## 15. The round the suite cannot play

`run-tests.sh` proves the plumbing and cannot touch the choreography: it forbids terminal automation, so the acts the tooling exists for — placing a tab, verifying a session, killing it — are out of its reach, and that gap is where the defects of the tab tooling were found. `tests/e2e.sh` plays one real round: a brief instantiated from the template and linted, a dispatch recorded, a session spawned at a tier, the tab placed against its anchor, the title guard exercised, the tab closed, the process confirmed gone, the record closed. It asserts the one thing no dry run can, that the tier named at dispatch is the model the live process carries. It is deliberately NOT part of the default suite. It drives the terminal, starts a session that costs tokens, and needs the app running with its API enabled: a suite that cannot run in a checkout with no window server is a suite people stop running. It skips itself off macOS and stops with a reason when the tooling cannot reach the app. It does not talk to the agent: verdicts and reviews need judgment and stay the orchestrator's.

## 18. A directive that outlives its decision is removed

The rule is the rulebook's (`skills/orchestrator/references/briefs.md`, « When a decision changes, the directives change in the same move ») and this document follows it: a decision since reversed leaves this file, and whatever a skill states is pointed at rather than restated. Six versions in ten hours had left four of them when the rule was written — one a section of this document contradicting another — and three commands had never been wired to what the last versions built.

## 19. A rotation leaves the old session alive until the new one runs

`rotate` spawns the replacement first and verifies it is running before the old tab is closed: a rotation whose replacement cannot start must leave the old session alive, since closing first is the one order that loses work (`skills/iterm-agents/SKILL.md`, « Safety order for a live rotation »). Running it found two defects that no dry run could reach. A tab can come back from creation before its session is attached to it: the tty is waited for now, re-fetching the app rather than trusting the copy in hand. And a title compared across a rotation always differs, because a working session rewrites it, so a rotation's guard is the stood-down acknowledgment and the tty, never the title. A failure whose mechanism is not yet named keeps its diagnostics: the check prints what the spawn said on stderr, so the next occurrence can explain itself. `rotate` refuses `--no-verify`: the verification is the rotation's whole guarantee.

## 20. A running process is not a launched agent

The operator supplied the evidence: a screenshot of an agent tab stopped on the host's workspace-trust question, and a note that every spawn stole the focus of whatever tab he was working in. A directory the host has never opened stops the session on a question whose highlighted answer is « exit », and from outside the session looks launched, because its process genuinely runs; so the launcher refuses such a spawn before making a tab, `--trust` records the answer for one directory, tabs are created unselected, and `screen --tty` shows what a stuck session displays (`skills/iterm-agents/references/commands.md`). **The intermittent spawn is explained.** One launch in roughly six returned no tty: a session on that question took a stray keystroke and quit before its tty could be read. After the fix, five consecutive end-to-end rounds ran with zero failures; it was never flaky, it had a cause.

## 21. The tab is born in the anchor's window, after the last agent

An anchor is resolved across every window before anything else has a side effect, and the tab is created in the window that holds it; an anchor given and not found is refused, never an append, because a tab that lands somewhere is worse than no tab once the script has said where it is. Each new agent goes after the orchestrator's last one, so a window reads left to right in launch order, through a chain file per orchestrator tty checked on the app's tab id, which is never recycled the way a tty is. The rules are `skills/iterm-agents/SKILL.md`, « Tab layout convention ». `ORCHESTRATOR_SELF_TTY` overrides the process-tree walk that finds the caller's own tab, so the chain's resolution can be tested where there is no terminal.

## 22. The tab runs its launch through a login shell

Every binary the package manager installs is on an agent's PATH, because an agent must be able to run the commands the operator runs: the app is asked to run the launch through the operator's login shell, while the launch still names the host CLI by absolute path so a profile that breaks PATH cannot kill it (`skills/iterm-agents/references/commands.md`). The alternative — a fixed `PATH` in the host's settings — would replace every session's rich environment (version managers, language toolchains) with a frozen list. The launcher is the one place that knows a session is being born, so the launcher is where the shell is chosen.

## 23. The operator decides; the orchestrator runs

A command the orchestrator could run is the orchestrator's to run: opening and tagging pull requests, running the live round, updating the installed plugin, restarting the sessions a change requires, pinning a head for review. What reaches the operator is an arbitration — what the thing is, two readings, what each costs, one recommendation — and a configuration change goes to the session that owns the configuration. Merging a pull request and taking it out of draft are the two exceptions: they are the operator's, on his clear and explicit request, never taken on green evidence or by « decide and move »; the orchestrator tells him « ready » and waits. When the orchestrator's own session lacks what the role needs, the repair is a successor spawned with the environment the task needs, not a favour asked of him. The rules are `skills/orchestrator/SKILL.md`, « The operator decides; the orchestrator runs ». The first of them came after an afternoon in which the orchestrator handed the operator three command lines — open this pull request, run this live round, refresh this credential: each justified by a limit of its session, none by its role.

## 24. A session is named at launch

The launcher passes the spawn's `--title` to the host as the session's name, so the title is the name every listing, the resume picker and the terminal show, not a transient tab label. The operator's ask, after the phase-4 implementer came up in the listing as the directory stem plus a reference, beside an orchestrator of the same stem: give agents and orchestrators names that tell them apart at a glance. The shape of a name is section 42; a brief still cites a session by name and reference together, because the reference is what disambiguates in every case (`skills/orchestrator/references/briefs.md`).

## 25. A hidden pane is still a session

A session behind a maximized sibling pane — the host extension opens its review views that way — is enumerated by every reader of the tool and listed as `hidden` (`skills/iterm-agents/references/commands.md`). And `close` closes the SESSION, never the tab: `tab.async_close` would have taken the review pane down with the agent, and with the extension in use that is a tab the operator is reading. A session closed alone leaves its siblings, and when it was the last one the app removes the tab itself.

## 26. A chain belongs to a session, not to a tty

A tty is recycled; a session id is not. Once, the successor orchestrator landed the probe LEFT of its own tab: the chain file for its tty held an entry a previous occupant of the same tty had written. So every chain entry now also carries `owner`: the app's session id of the orchestrator that wrote it, and a chain read live keeps only the entries whose owner sits on the tty now; entries naming another owner, or none, are dropped and the file rewritten. The file keeps its name, because `self` still resolves to a tty and a file per tty is what `close` sweeps. A dry run has no app and no session id; `ORCHESTRATOR_SELF_ID` stands in for it.

## 27. The successor inherits the orchestrator's model

The succession command spawned the successor at the `deep` tier, so a succession re-routed through the operator's map and silently undid a model he had set by hand. The operator's ruling: no default model — the successor inherits the orchestrator's model, and the one in use now, not the one the session was launched with. The hooks module records the model that answered the last turn in the measure file (section 3.2); `--inherit-model` reads that file of the calling session (`CLAUDE_CODE_SESSION_ID`) — under the config dir, never the state override, for the measure file is the module's own artifact (section 4.4) — and types that id as `--model`, exclusive with `--tier` and `--model`. Without a measure file, or with one that carries no model or the module's `unavailable` sentinel (written when the host gave it no model), the spawn refuses and names the module: a succession must not guess a model, and the ruling forbids a default. The tier map keeps binding what it binds — implementers, reviewers, probes; an orchestrator's first instantiation is the operator's launch, and its model is his choice from then on.

## 28. The orchestrator never implements through a subagent of its own

A subagent's diff is the orchestrator's own diff, and its reviewer would be its writer; the method rests on the writer and the reviewer being different sessions. The rule, and why a plan-writing skill's execution header is boilerplate to replace rather than an order to obey, is `skills/orchestrator/references/briefs.md`, « Standing rules (put in every prompt, enforce in every review) », carried in the succession brief's first paragraph for a successor that reads its brief before the rulebook. The suite refuses a document under `docs/` that opens with that foreign header.

## 29. The library's tracebacks are filtered at their source, and nothing else is

Getting the app object subscribes it to layout and focus notifications, and the API library dispatches each notification as a task of its own. When a step's coroutine returns, the library cancels its helper tasks without awaiting them and the socket is closed; a helper task mid-flight ends on the closed socket, and its exception is reported when the finished task is collected — by the event loop's default exception handler, which writes through the standard logging module under the `asyncio` name. Two earlier attempts read the loop and did not hold: a settle step found no pending helper task, because the failing tasks are either not yet dispatched or already finished. The suite's stub made it green by creating helper tasks by hand, a timing that never occurs against the app. So the module installs, at import, a filter on that logger that drops a record whose message starts with « Task exception was never retrieved » and whose exception class is named `ConnectionClosed…`, and passes every other record: a diagnosis the stream exists to carry is not of that shape. Measured on a live spawn against a control: the known lines gone, every other line kept.

The launcher's other readings follow the rule this section's history taught: a gate that cannot measure holds nothing, and says so. A reading that never comes — a transcript not yet written, a record that cannot be read — lets the launch through with a line on stderr, never a silent pass and never a refusal. One of those readings is now a named exception: a permission mode that never gets read is refused rather than let through, the tab closed the way a mismatch closes it, because a session nobody can read may be parked on a dialog or hung at start, which the plugin already calls not launched (§43).

A launch carrying neither `--prompt` nor `--prompt-file` (nor `--brief`, which builds one) could only ever fail this timeout, since the host writes no transcript before a first prompt — so it is refused up front, before any tab is made, rather than waiting it out.

## 30. A checkout per phase, with the project's local material

Two rules of the method were held by discipline alone. « One writer per repository » queued every dispatch behind the orchestrator's own checkout, and a sandbox that should let an implementer write under one root could not, because a git worktree writes into its source's `.git`. A clone contains everything it touches, and a clone per phase turns the one-writer rule into a fact (`skills/orchestrator/references/briefs.md`, « Prerequisites and phase rules »). A clone carries only what git tracks, so the project's local material — its settings directory (never the operator's own `settings.local.json`, which stays his), what its exclude file keeps out of history, what its manifest names (`skills/orchestrator/scripts/workspace.sh`, its header comment) — is copied as part of making the checkout, not as a step after it, which by hand was done only sometimes. What is left out on purpose: several implementers on one repository, a `--workspace` flag, and cleanup by age.

`skills/orchestrator/scripts/workspace.sh`, bash 3.2 like its neighbours; the root is `ORCHESTRATOR_WORKSPACES`, else `~/dev/workspaces`, and a checkout lives at `<root>/<repository name>/<name>`.

- `create <source> <name> [--base <ref>]` prints the checkout's path on stdout and nothing else there. It refuses a source that is not a git repository, a name outside `[A-Za-z0-9._-]`, a target that already exists (a stale checkout is deleted on purpose, never overwritten) and a base the source does not know. It clones from the local repository, points the clone's `origin` at the source's `origin` so the implementer's push reaches the real remote, copies the local material, and leaves nothing half-made: a copy that fails removes the clone and names the error.
- `delete <path> [--discard]` refuses a path outside the root, always. It refuses a dirty tree or a commit on no remote branch unless `--discard` is given, the guard that keeps a shelved phase's work from vanishing before anyone said so.
- `list` prints one line per checkout under the root: path, branch, short head, `clean` or `dirty`, `pushed` or `unpushed`. It is what a successor reads to know what is lying around.
- Every refusal is one line `workspace: <reason>` on stderr and exit 1, the launcher's contract. The script never writes the trust record (that is `spawn --trust`), never launches anything, never touches the source.

Every listing of the source's local material is read NUL-separated (`ls-files -z`), because git quotes and octal-escapes a name that is not plain ASCII by default and the copy would read a path that does not exist; the sweep reads the repository's default branch from `origin/HEAD` alone, with no network call and no guess, since it runs inside the stop gate on a deadline.

Never copied, even when listed: `.git`, `node_modules`, `vendor`, and anything `.gitignore` covers that the manifest does not name; build trees and caches rebuild, and copying them makes a huge checkout and copies secrets by accident. `create` says what it copied, one stderr line per category with a count, and keeps the copied material out of the checkout's own history the way the source keeps it out of its own, so a checkout does not read dirty from birth. The root must be writable under the sandbox for implementer sessions and readable for the orchestrator's clone, a request to the session in charge of the host's configuration.

## 31. The trust record is the host's file too

Three readings of the trust gate (§20), taken once a checkout per phase made the gate run at every dispatch: a record that already said yes was rewritten anyway, a record the launcher could not read launched past the question in silence, and entries outlived their directories. So a recorded directory is never rewritten, an unreadable record lets the launch through and says so, and `trust prune` lists the entries whose directory is gone before `--apply` removes them, because the file is shared and a write is a decision (`skills/iterm-agents/references/commands.md`). The script that makes checkouts never touches this file; pruning is the launcher's, beside the writer.

## 32. The model that answers is read, not assumed

Once, the host switched a running orchestrator from the operator's chosen model to a fallback after its own classifier refused one message, and told nobody: the launch line, the process line and the status line still said the chosen model, and the only trace was the transcript, where every assistant entry carries the model that produced it. So the module reports the model that answered last: the measure event's model is the figure the host itself carries, the last assistant entry's `model` is the trace that once caught it, and `unavailable` is said rather than a line left out. The module keeps the last model in its own memory: the first reading is kept in silence; a reading that differs makes one line, shown as a toast and put in the context of the session's next prompt, in every session whatever its role — the channel every gate line reaches the model by, since a toast alone fades unread — saying which model answers now, which one answered until now, that the operator must hear of it in the next message, and that a succession does not repair it — so a switch back is said too and a drift that holds is said once, and a module reload, which has measured nothing yet, says nothing on its first reading. What is left out on purpose: comparing against the launch line's `--model`, since the kept reading is enough and what matters is a change, not a distance from an intention; and naming the refusal's category, which would read as a verdict on the message when the drift is the fact. Any automatic action on a drift: the operator decides what a session on the wrong model does next, and the plugin takes none.

## 33. The installer reads the stored command through its home spelling

The installer unwraps a tap a previous install left by comparing the stored status line command with the tap's own spellings, and the tap's path is expanded. An operator who keeps the configuration directory in a repository writes the home as `$HOME` or `~`, which the host expands when it runs the line; compared as text, the installer reads a wired file as unwired and leaves the tap in place. Before the comparison, the installer normalises the command it reads — a leading `$HOME/`, `${HOME}/` or `~/` becomes the expanded home, and nothing else in the line changes — and the stored line is never rewritten: which spelling a settings file uses is the operator's choice, in a repository the plugin does not own. What is left out on purpose: detecting a doubled tap already written by an earlier run — that file is the operator's to fix by hand.

## 34. A successor takes the predecessor's place, chain included

The layout convention once promised that a successor spawned `--right-of self` « sits between you and your agent »; with agents open it landed past every agent, joined the predecessor's chain as if it were one, and its own next spawn landed left of the agents it had inherited. A successor is not an agent: `spawn --successor` places it immediately right of the caller, the chain ignored, and hands the predecessor's own chain entries over to it (`skills/iterm-agents/SKILL.md`, « Tab layout convention »). The chain is handed over only once the successor is verified running: a spawn refused after its tab exists closes the tab it made, prints its tty, says whether the close happened, and leaves every chain as it found it. If the new session cannot be read in the seconds after creation, the launch stands and one stderr line says the chain stayed behind and how to place the next agent by hand. A step that must never be forgotten belongs to the launcher rather than to a template: the hand-over is the launcher's, so a successor that forgets a step cannot lose it. The same holds for the entry that names the caller's own tab in an orchestrator's chain (written when that orchestrator spawned it, `--resident` mark included): the launcher re-points it, in every chain that holds one, to the successor's tab and tty with owner and mark kept, so the orchestrator's stop gate and `--right-of self` never read a closed tab, or a recycled tty's stranger, as its resident agent.

## 35. The settings directory travels through the exclude file, and a base may be the remote's

Two findings from the sibling build that runs the same script on a larger repository: copying the settings directory whole would have carried the host's own worktrees, 4.2 GB, into a checkout meant to hold a phase, and a source whose local base lagged its remote handed the phase a stale base with no way to name the fresh one. Inside the settings directory, the exclude file's patterns say what does not travel: a pattern that reaches inside the directory names something the host generates, while a pattern naming the directory as a whole (`/.claude/`, `.claude/`, `**/.claude/`) says only that the directory stays out of history, which every copied file already does, so it is set aside. The files are listed by git and copied in one pass, never the directory whole, and `create` says both counts. A base is a local branch of the source or one of its `origin/` refs: `--base origin/main` resolves against `refs/remotes/`; any other remote is refused, because the checkout's `origin` is the source's; the remote's head is fetched into the checkout from the real origin, and the source is never touched. A bare commit id or a tag is refused: a phase branch stacks on a branch. What is left out on purpose: reading `.gitignore` for the settings directory — a project that ignores it there says nothing about what inside it is local material. The operator's own `settings.local.json` never travels either way, whatever the exclude file says about it: the permission rules it holds — a squash-merge, an undraft, a pinned-lease push — are his session's, never an agent's, and the copy's stderr line says how many were withheld for that reason.

## 36. A reader's pinned copy is a detached worktree; a clone is for a writer

The clone per phase exists for two reasons that concern a WRITER only: sandbox containment and one writer per checkout. A review reader, or an instrument the orchestrator runs itself, writes nothing, is confined to no root, and needs none of the project's local material but the norms its global excludes keep out (section 37) — least of all the orchestrator's own briefs and state file, which a clone of this repository would carry into a reviewer's copy. So a reader's copy is a detached worktree of the orchestrator's own checkout, at exactly the head under review (`skills/orchestrator/references/review.md`, « Review on evidence »), made and removed by the script (section 37). A delivered implementer is not kept for the fixes a review may order, whatever the tab is called (section 45).

## 37. A pinned copy for a reader, made and removed by the script

The first review run under that rule showed the two things a by-hand step always shows. The copy was one `list` did not know and `delete` would have removed leaving the source's worktree metadata behind, and the suite read the worktree's `.git` file as a machine path. `workspace.sh pin <source> <name> <ref>` makes the copy under the same root with the same naming as `create`; the ref is anything the source resolves to a commit — a branch, an `origin/` ref, a tag, a commit id — refused when the source does not know it, since a pin names a head and a head is a fact. It runs `git worktree add --detach`, then copies the files the operator's global excludes keep out of the source, the ones `create` copies (section 40), the project's instruction file among them — two review sessions once read the code without the project's norms — and no other local material: nothing of the settings directory and nothing the source's own exclude file keeps out, where the orchestrator's briefs and state live; no remote change. In `list`, a pin's line carries `HEAD` as its branch and `pinned` in place of `pushed` or `unpushed`; `delete` refuses a dirty pin, or one whose head is on no branch of the source, without `--discard`, then removes the worktree so the source forgets it. The machine-specific grep excludes a file named `.git` as it excludes the directory, so the suite reads the same in a pin as in a clone. Pinning a directory outside the root; a pin that carries any other local material, since a reader that needs a project's environment file is running an instrument, which is the orchestrator's to prepare: both out of scope on purpose.

## 38. A session knows its own tab, and moves only what is its own

`list` marks the caller's own row `self` and shows each session's name beside the tab title, and `move` refuses a target that is neither the caller's own tab nor in its chain unless `--force`, which says what it moved (`skills/iterm-agents/references/commands.md`). A session the caller did not launch is not its to place: an orchestrator that had never measured its own tty took the last tab for its own and moved a stranger's session between itself and its agents.

## 39. A successor carries the orchestrator's name, and a title has a shape

Two reports, one machine each: one predecessor spawned its successor with `--title steward-successor`: the launcher took it, and the successor came up under that name in every listing; another spawned its successor with a plain anchor, and it landed at the far right of the window with no chain. A title has a shape the launcher holds it to (section 42). A successor spawned without a title takes the caller's session name — the host's record of the session first, which holds a name given by a rename, then the launch line's `--name` — so every brief that cites the orchestrator still cites it; a caller whose name cannot be derived is refused and the title typed in the house format. An orchestrator's title with a plain anchor is refused, because the plain anchor lands after the chain and a successor spawned there is the far-right tab the operator saw. A successor comes up under remote control with its name, because the operator drives his orchestrators from the host's remote client too; an agent never does (section 44). `rotate` forwards every argument it does not consume, `--trust` included. The rules are `skills/iterm-agents/references/commands.md`.

## 40. The operator's global excludes are local material too

One file travelled by hand on every live run of this family: the project's instruction file at its root, kept out of history not by the repository's exclude file but by the operator's global one. `create` reads the global excludes file the source's git configuration names (`core.excludesFile`, else the host's default location), copies what it keeps out of the source, and adds its patterns to the checkout's own exclude file, so the copy stays out of the checkout's history; the stderr line counts those files apart from the repository's own.

## 41. What the live rounds paid for, in text

Four readings of the live rounds each became a sentence where it binds: a stand-down acknowledgment that reports anything uncommitted is an unfinished delivery (`skills/orchestrator/references/lifecycle.md`, step 4); a reader writes no git configuration and carries every path inside each tool call (`templates/agent-review-brief.md`); a brief's context line names the agent's own measure file, never a checkout of this repository (`templates/agent-review-brief.md`, `templates/agent-comments-brief.md`; it named the plugin's installed gauge script until the hooks module replaced both the script and the rule); and a fresh tab reads « Chat » for a few seconds before the session names itself (`skills/iterm-agents/SKILL.md`, « Reading the tabs »).

## 42. Short names, chosen servers, and a hand-launched orchestrator named on the spot

Three rulings by the operator on the evening 0.25.2 shipped, after reading his window: names too long to read, every agent loading servers it never used at about 70 MB each, and an orchestrator he had started by hand that no listing could recognise. A name has three roles — `Orch : <subject>`, `Agent : <subject>`, and, under `--auditor` only, `Audit : <subject>` — the subject at most twenty-five characters, and the launcher refuses anything else; `--title-free` is the probe's escape from the shape. An agent's servers are chosen per agent from the operator's catalogue, `<state dir>/mcp.json`, under a strict launch by default: the catalogue copies server definitions rather than switching scopes off, because measured, no setting removes a user-scope server and the strict flag alone removes every server of every scope. A session the operator starts by hand is named when it declares itself: the host gives the model no rename of its own, so the plugin's `rename_session` tool records the name the model chose and the module runs the host's `/rename` with it when the turn ends — the host refuses a command run from a hook the turn is waiting on — so the session calls it once and ends the turn, and dispatches from the next, under its new name. The rules are `skills/orchestrator/references/lifecycle.md`, `skills/orchestrator/SKILL.md`, « Overview », and `skills/iterm-agents/references/commands.md`.

A later ruling (2026-09-30) answered a fourth: a spawned agent could not reach the account's own Slack connector, because the strict launch excludes every scope but the catalogue's file, and the account's connectors — the ones a session the operator opens by hand already loads — live outside it. `--account-connectors` drops `--strict-mcp-config` for that one chosen spawn, so the session also loads every connector of the account, not one of them; the catalogue's chosen servers still travel exactly as before, on the same file. Dropping strict reopens the project's own "enable these MCP servers?" dialog that strict had made moot, so the launch pre-answers it again for that spawn (`enableAllProjectMcpServers`, the setting this section's launch retired when the catalogue took over, now reintroduced guarded by this one flag and nowhere else). Off unless asked: without it the launch is unchanged, byte for byte. `rotate` forwards it like any other spawn option. A launch also names the tools the session is not given and carries the host's cuts in its one `--settings`: §65.

## 43. The mode a session came up in is read, not believed, and the screen is read from the bottom

The host applied the permission mode asked to every session on two tiers' models and to none on the third's, which came up in default mode with the flag accepted and ignored; two agents stood on a permission prompt in tabs nobody watched. So the spawn reads the mode on the session's own transcript and refuses a launch whose mode differs, closing the tab it made and naming the repairs, and a session nobody watches runs in the operator's decision mode (`skills/model-routing/SKILL.md`, « Pairs, tiers and the map »). A transcript that has not appeared by the timeout refuses the launch too and closes the tab the same way — the named exception section 29 states. A launch with no startup prompt at all is refused before that timeout is even started, for the same reason (§29): no transcript, ever, without a first prompt. `screen --lines N` returns the last lines, because a blocked prompt sits at the bottom of a tall terminal.

## 44. An agent comes up with remote control off

The host starts remote control for every new interactive session when nothing is set. The operator read his remote client and found an agent in it, a session an orchestrator had spawned with no `--remote-control` on its launch line. Measured with a debug log, a launch setting turns it off and the flag wins over the setting. So the launch carries the setting whenever it carries no `--remote-control`: every spawn that is neither a successor nor an auditor, and a successor spawned with `--no-remote-control`. A plain successor and every auditor carry `--remote-control '<its name>'` (sections 39, 52), as `iterm_agent.py`'s own comment says.

## 45. The closing round: what the deferred list held

One round closed everything the live rounds had deferred, each item fixed or closed with its reason.

- **A delivered implementer is stood down at the verification of its delivery**, never kept through a review round; a review finding goes to a fresh session with a resume brief, and a next phase dispatched at that verification is the only reason it stays (`skills/orchestrator/references/lifecycle.md`, step 4).
- **A subject neither starts nor ends on a space**, so a listing never shows a name that reads as empty or one the operator cannot tell from its trimmed twin (`skills/iterm-agents/references/commands.md`).
- **The files a launch leaves carry their kind in their names.** A launch leaves three files under `prompts/` — `launch-<title>-<ms>.sh`, `mcp-<title>-<ms>.json` and `prompt-<title>-<ms>.txt` — so the three sort by kind and a directory listing says what each file is.
- **The library's stderr noise is filtered at its source** (section 29).
- **The predecessor's last message is the successor's signal to close its tab.** On the takeover confirmation the predecessor sends « handed over » as its last message and ends its turn; the successor closes the tab on it, or on a reading of the tab's screen after five minutes, never on the host's idle notice (`skills/orchestrator/references/lifecycle.md`, « Your own context (the orchestrator is not exempt) »). Measured on one succession: the successor waited for an idle notice that reaches a working session only when its own turn ends, and it arrived a quarter of an hour after the predecessor had finished.
- **A hand-started predecessor is closed like any other, nothing asked.** The successor always closes its predecessor, one the launcher did not open included, with `close --tty --expect-title` on the title `list` printed for it; where the host refuses that close, the successor asks the predecessor to call the module's `end_session` tool, which ends its session when its turn ends, and proves the end on the tty — `verify --tty` failing, or no host CLI under `ps -t` — never on `list`, which keeps the row of a tab left holding a shell (`templates/orchestrator-succession-brief.md`, step 4). Measured on one succession: the host's own safety check refused the close as interfering with a workload the session had not started, because the plugin did not launch that tab. The operator's first ruling (2026-10-01) was to ask him up front; a predecessor then stayed open for hours beside its successor, under the same name, while the successor waited for a « close it » nobody was asked to give again, and his standing order replaced the question with the module's end.
- **One marketplace, the family's** (section 8).

Closed without a change, with the reason:

- The 25-character cap counts code points, not graphemes: the subject is typed by an orchestrator in the house format, no listing has shown a combining sequence in one, and the standard library carries no grapheme segmentation to count with.
- Two transcripts born in the same instant tie on their path: the launcher launches one session at a time and waits seconds for the host on its tty, so two births inside the filesystem's timestamp resolution are not a case it makes.
- An empty `permissionMode` string is read as absent: the host writes a mode name, and a value that says nothing is judged as unread, which now refuses the launch and closes the tab the same way, said with the word (section 29).
- The dry run's stdout does not tell « no catalogue » from « empty default »: the stderr line is that reading, the stdout describes the launch, and the suite reads both streams.
- `ORCHESTRATOR_PS_TABLE` is honoured on a live run: every `ORCHESTRATOR_*` override is read the same way and is the suite's door and the operator's alike, and a guard on one of them would be a false comfort about the rest.
- `list` spends up to ten seconds on a tty whose process table does not answer: the bound is on `ps`, a tty that does not exist answers at once with nothing, and the wait has not been observed.

## 46. An app that stops answering is named, not waited on

One right-click left a context menu open in iTerm2, and for four hours every launcher call hung while the terminals kept scrolling. A menu runs a nested event loop during which the app dispatches no AppleEvent, and the API library's authentication is a blocking read no timeout inside the call could reach. So the bound is taken outside the library, before it is entered; the launcher tries two rungs, `api` then `applescript`, and says which served; when neither reaches the app it samples the main thread and names the cause with its remedy; and a close is proved on the process table, not on the app's acknowledgment (`skills/iterm-agents/references/commands.md`, « When iTerm2 does not answer »). The `applescript` rung selects the operator's tab again after its `create tab`, which selects the tab it makes, so a launch leaves the operator where they work on either rung. `ORCHESTRATOR_BACKEND` pins one rung, and an unknown value is refused rather than read as the default. The suite pins `ORCHESTRATOR_HOST_CLI`, which is read from the environment at import, and the operator's own shell carries it as an absolute path: the same tests were matching two different names depending on whose machine ran them.

## 47. The operator's word comes first, and it is answered

The operator's primacy and the seven duties owed him while he rules are `skills/orchestrator/SKILL.md`, « The operator's word comes first, and it is answered », which sits above every other section because it outranks them. Three of its rules stand out because their earlier forms read otherwise. Every question gets an answer, in order, before any tool call, the one exception a question on the state of an artifact, which gets one short re-reading command first. On the third ask of the same question the session re-reads its own earlier messages first: if it had answered clearly, the operator missed it, and the answer is given again in full, at the top of the message, alone, with no hand-over offered; if it had not answered, or answered beside the question, it says so in one sentence, answers, and offers the hand-over to a fresh session. And only an explicit instruction of his on the very point outranks a rule: a deadline, a wish or a question is not an order to break one; an instruction that does bear on the point wins, the contradiction said in one line; the tooling's deliberate refusals are never routed around; and what would end a session or change the machine stays a STOP-and-ask.

The duties also travel in the succession brief. A successor reads its brief first and can act on it before it loads the rulebook, so a duty living only in the skill is lost at the first succession; the suite checks both files carry them.

## 48. An agent is an iTerm2 tab, and a name that cannot be read is not invented

A session that is not a tab in the window the operator reads is not an agent he can see, place, close or account for, and a launcher that quietly hands him one has hidden a fault that has a one-keystroke remedy: the launcher has two rungs and no third, and a launcher failure is reported, never routed around (`skills/iterm-agents/SKILL.md`, « An agent is an iTerm2 tab, always »). A name is read first from the host's own record of the session (`<config dir>/sessions/<pid>.json`), which holds a name given by a rename too, its surrounding quotes stripped; without one, it is read from the process table to a bound, or not at all: `ps` hands back a flat command line, and the quoting that made `--name` one argument is gone, so `--name` goes last in the launch and a reconstruction longer than forty characters is listed `(name unreadable)` — a different fact from `(host default)` — rather than a name invented by wherever the words happened to stop, which an orchestrator would then address.

## 49. The caller is not always in the app

A session running in another terminal still has a tty, and the app simply has no session on it. The chain is the app's and cannot be kept for a tab the app does not know. That is a fact to state, not a reason to fail: a spawn from such a session keeps no chain and says so. A traceback is not an acceptable answer at any frequency. This section first justified the fix by claiming that the operator's ruling made a caller outside the app « the case that has to behave », a ruling given the hour before; he struck it out, because a ruling that forbids making something makes it rarer (section 50).

## 50. A repair is justified by what is broken

A repair is justified by the thing that is broken and by nothing else, and a justification's direction is read before it is written: a rule that forbids something makes it rarer, not commoner. The rulebook carries both as rationalizations and a red flag (`skills/orchestrator/references/review.md`, « Depth vs scope, and the rationalizations observed »; `skills/orchestrator/SKILL.md`, « Red flags: STOP »); section 49 is the case that taught them.

## 51. A self-anchor the app cannot resolve is lost, not fatal

A NAMED anchor the app does not know is a tab the caller got wrong, and refusing it stays right. The caller's OWN tty with no session of the app's on it is a different reading: the caller runs in another terminal, and « place the new tab beside me » has no meaning there. Refusing that case blocked the one spawn that exists to end it. A session outside the app could not spawn its own successor, the succession ordered to bring it back into the app. The anchor is dropped, the new tab lands where the app puts it, and the drop is said with its tty — which keeps the successor carrying the name derivation and the remote-control flag that `--successor` alone provides.

## 52. The audit of an orchestrator

An orchestrator's deliveries are read by its reviews; its METHOD was read by nobody. The first audit of a live build was run by hand, by a second session the operator pointed at the first, and it found defects of the method's kind. The operator asked for the instrument: `commands/audit.md` launches it, `templates/agent-audit-brief.md` holds the auditor's terms.

**Why it was redone.** Its first form ordered changes to the orchestrator, which applied them, and kept a method file of its own. On another project it issued 101 orders in 18 days, almost all of them new rules: it reacted to the incidents everyone saw and never to the time lost a little at every step, never ran the loop « change, measure, keep or undo », and ended up auditing its own rules. The role was right; ordering without a cost and without an end was not. It now proposes and the operator decides.

**What it does.** It starts from the stock — what is in place, what it costs, what it has yielded — shows the net balance — lines added and removed under the product against the instruments, time in gates against time producing — re-reads the figure of each proposal the previous audit made, and proposes at most five changes, each « remove X » or « restore Y » with its expected gain, its cost and the figure that will check it. Removing is proposed as freely as adding; adding asks for a product defect as its evidence. It writes one report under the briefs directory's `audits/`, tells the operator, and stops. The report keeps a dated name, because successive reports of one subject must not collide and the previous one is the newest, but its date is the output of `date +%F` run at launch, never typed; the auditor's brief is named by its subject alone.

**What it does not do.** It writes no other file, applies nothing, orders nothing and messages no session. The orchestrator's skill says nothing about it: a proposal the operator relays is his word, like any other. There is no end command: the audit ends by itself, and the operator closes its tab. **Kept on past its report.** An operator who keeps the auditor working after its report (an annex, a proposal to relay) meets its gate with work in hand: the hook's `Audit :` line then says to succeed, not to stop. The auditor writes the succession brief (`templates/auditor-succession-brief.md`, the report's path and what the operator gave it after it), spawns its successor with `spawn --successor`, waits for « takeover confirmed » and answers « handed over »; the successor closes its tab. The launcher derives the successor's `Audit :` name from the caller's, as for `Orch :`, places it immediately right of the caller (so, once the predecessor is closed, in the auditor's own place left of its orchestrator), and hands and takes no chain. With no work after the report, or before it, the rule is unchanged: the one report, then stop.

**An auditor is a third kind of session** for the launcher: `spawn --auditor` places it immediately left of its caller, on the caller's model and under remote control, but writes it into no chain, because an auditor written into the chain would become the anchor the orchestrator's next agent lands after (`skills/iterm-agents/references/commands.md`). Its place is read after the spawn and repaired if wrong: the launcher lists the real tab order, moves the auditor left of its caller when it is not there, reads again, and if it is still wrong says so on stdout with the `move` that repairs it and exits non-zero, the session kept; a listing it cannot read, or a terminal whose API cannot serve the move, is said as such rather than as a misplacement.

**Its instrument.** `rhythm.sh` reads the net balance from git alone: merges per week by type, and lines under the product's globs against the instruments'. Two readings of its first version were wrong on a real repository, each repaired with a fixture case seen red first: a pathspec that stopped `*` at a slash, and a bare `YYYY-MM-DD` that git completes with the current time of day, now written `YYYY-MM-DDT00:00:00`. The default branch is read from `origin/HEAD`, else from the remote's own answer (`ls-remote --symref origin HEAD`, one bounded call), else guessed (`main`, `master`, the branch checked out); a branch not read from `origin/HEAD` is named on stderr, so a figure built on a guess is never silent, and a guess says whether the remote did not answer or named a branch this clone does not have.

## 53. A method he names is a format, and a fact not read is not stated

Duties 5 and 6 of the operator's word (section 47): a method the operator names binds the presentation as well as the judgment, and a name, a role, a figure or a cause comes from an output of the session or is said to be unknown (`skills/orchestrator/SKILL.md`) — a named method nobody opened once produced a summary with no assessment, and a name no command printed was once stated as fact. The comments section of the review reference points at duty 5, and both duties travel in the succession brief.

## 55. A pull request is ready only when the record says a round read its head

Both readings of a delivery — the review round and the project's norms tool (`skills/orchestrator/references/review.md`) — were skipped three times in one day, and two pull requests were one command from leaving draft on that evidence. Nothing was wrong with what the rule said; what was wrong is where it lived. A rule prose alone carries is applied from memory, and on a day with three rounds in flight it is remembered by the session that has the most context to spare, which is never the one at the gate. It needed a refusal a script can make. So the round's reading lands on the dispatch record, and `dispatch-record.sh ready` answers one question, whether the last review read the head in front of the orchestrator; its subcommands are `skills/model-routing/SKILL.md`, « The record ». The gate is blind past its facts on purpose: whether the findings were verified and whether the operator approved stay the orchestrator's and his, and a green `ready` is not an approved pull request.

The screenshots a frontend pull request owes went the same way: written in the rulebook, the phase brief and the review brief, and still five front-office pull requests were declared ready without one image, two « skipped » for lack of data on the reference account and three never shot. So the row also says whether its pull request changes what a user sees (`surface`), and `ready` refuses a row that says nothing and reads the description of a `--ui` one, refusing it with no image. Counting images is all a script can see; whether they show the surface the diff changes stays the review's and the orchestrator's.

Counting them was then shown not to be enough. On one day three captures that showed a defect — a map button whose icon sat off-centre and whose style matched none of the controls beside it, a reset button pushed onto a row of its own with its right edge past the controls above, an « after » image with stray text left in a search field — were each read by an orchestrator and passed, because the phase brief, the review brief and item 12 asked only whether the images were there, showed the surface and used the right account. Nobody was asked to look at an image for a defect. So every capture is now audited against one checklist — edges aligned with their neighbours, icons and text centred, no stray text in an input, nothing truncated or overflowing, no unexpected extra row or space, each control consistent with the ones beside it, both viewports — by the implementer before delivery, by the review round, and by the orchestrator itself before its verdict, each image getting one line, clean or its defect; a capture that shows a defect is not delivered, it is fixed and retaken. The orchestrator's own audit lands on the row: `dispatch-record.sh audit <record> <id> --head <sha> --images <n> [--defect "<text>"]...`, a new one replacing the last, a review round leaving it in place. On a `--ui` row, `ready` refuses with no audit at the head in front of it or at the reviewed or fixed head it accepts, with an audit that opened fewer images than the description carries, and with an audit that recorded a defect; `--minor` and `--none` rows are not held to it. Whether the audit was an honest look stays the orchestrator's; the record only makes it a step that cannot be forgotten.

The proof end to end went the same way. A frontend pull request was merged and deployed and did not work there: its only proof was a browser pass the implementer reported, nothing a reviewer could replay, and neither the report nor the « ready » said there was no E2E test. So, on the operator's order, every pull request carries an E2E test as far as one can be written — a backend one against the service brought up in a container, a frontend one a Playwright test committed in the project's test tree — or says plainly `E2E: none — <reason>`, and silence is not ready (`skills/orchestrator/references/briefs.md`, standing rules; `skills/orchestrator/references/review.md`, item 14). The line lives in the implementer's report and the orchestrator's « ready », never in the pull request's description, which holds its codified sections and nothing more. `ready` takes it (`--e2e`), records it on the row and refuses silence; `E2E: none` passes only with the operator's validation of that pull request ready without one (`--e2e-waiver`, his words and their date) or his exemption of every pull request of the session (`exempt`, recorded once beside the record), after which the orchestrator decides alone. Whether the reason holds is the review's and his; the script refuses only what is unsaid or unvalidated.

## 56. A state is re-read in the turn that asks about it

The seventh duty (section 47): nothing is asked, proposed or reported as pending before its state, and the premise the question assumes, are re-read on the artifact in the same turn; the state file is refreshed from the artifacts at every quiet boundary (`skills/orchestrator/SKILL.md`). No script and no polling: the re-reading is the command the question already needs, run in the turn that asks it, and a watcher that refreshed the file on a schedule would only move the stale reading from the file to the watcher's last pass. `decide` verifies each item when it collects the round and again when it presents it, and `progress` corrects the state file where the artifacts disagree (section 6).

## 57. A tier is bound to a family, and the launcher says when it is not

A tier is bound to a family alias, never to a versioned identifier, which goes stale without a sign (`skills/model-routing/SKILL.md`, « Pairs, tiers and the map »). The launcher reads the binding on every dispatch, so it is where the drift can be seen: it warns in one line on a versioned binding and launches anyway. It never refuses and never rewrites the map: a pinned model may be exactly what the operator wants for a while, and the file is his. The detection names no family, so the plugin still carries no model name.

## 58. One review round, one correction round, and ready is the operator's turn

The orchestrator's process on a pull request it dispatched is one review round, its own triage, one correction round it verifies itself on the artifact, and done; rounds of review repeated until nothing is left are the operator's own process, when he runs reviews by hand (`skills/orchestrator/references/review.md`, « Thresholds a verdict never crosses »). Rounds that repeat until nothing is left converge on nothing: each one reads the previous fix, finds something in it, and orders a fix of its own, and a finding nobody had to fix ships as churn. The gate follows the rule: `fixed` records the one correction round at the verified head and warns on a second, and `ready` passes at the reviewed or the fixed head. Ready from the orchestrator's side includes the rebase on the main branch, each pull request of a stack on the one below; then « ready » is told, and his review, taking the pull request out of draft and approving the squash-merge are his by default (`skills/orchestrator/references/review.md`, « The rebase, once ready »).

## 59. A frontend surface is proved by a browser run and screenshots on the pull request

A green suite and a read diff say what the code does, not what a surface shows: a layout that collapses or a screen that does not match the spec passes both. So, on the operator's ruling, a pull request that creates or substantially modifies a frontend surface, or creates the interface of a new feature, is tested in a real browser with Playwright and carries screenshots of the surface on the pull request (`skills/orchestrator/references/briefs.md`, « Standing rules (put in every prompt, enforce in every review) »; the review check is `skills/orchestrator/references/review.md`, item 12). The rulebook carries it as a standing rule and a review item; the phase brief carries the clause for the implementer, who does not read the rulebook, and the review brief the check for the round. What is left out on purpose: no script, no hook and no tooling for screenshots, and no named upload mechanism. What the suite reads: in the rulebook, the phase brief and the review brief, the trigger phrase verbatim, the minor exemption, where the screenshots go, the stop without a browser, the review check, the excuse and the red flag, each check falling when its sentence is removed or reversed. The audit every capture owes, its checklist and the record that gates it are section 55's.

## 60. The launch can set one session's gate

The operator's ruling (2026-10-02): 300,000 tokens by default, and a parameter changes the value. `spawn --gate-tokens <N>`, which `rotate` forwards, takes a positive integer and refuses anything else before a tab exists. The launch then exports `ORCHESTRATOR_CONTEXT_GATE_TOKENS=<N>` beside `ORCHESTRATOR_SPAWNED=1`; without the option nothing is exported and the default holds. The variable is the one the module's context gate reads, so the launcher adds no new reader: the gate of a session inherits what its launch exports, as the push guard's marker already showed (the status-line tap that once read it too is gone with the tap, section 3). The option takes effect on a window of 1,000,000 tokens or more only, because the gate reads the token gate there alone; below, the percentage gate of the window decides. With `--brief`, the startup prompt says « Your context gate is <N> tokens on a window of 1,000,000 tokens or more » and that below it the window's percentage gate holds (a `--prompt` or `--prompt-file` spawn gets the export, not that line) so a brief's « past 300,000 » is read against the real value; the brief is not rewritten. A successor does not inherit its predecessor's gate: it carries one only when the option is given. There is no per-role default and no configuration file.

## 61. A temporary directory is cleaned once its purpose is over

The operator's order (2026-10-02): a temporary directory that is no longer useful — review done, pull request merged, or other — is cleaned automatically. Until then every cleanup was a manual step of the orchestrator's after a stand-down, and what was missed stayed: the workspaces root held checkouts of merged pull requests, the host's per-user temporary area held one directory per checkout ever used, and a reviewer's removal of its own scratch was refused twice by the host's guard on the working directory, the agent being inside it.

What is deleted, when, and by whom:

- **A checkout or a pin, by `close`.** `close` reads the host CLI's working directory on the tty before the close; once the process table proves the session gone, when that directory is a checkout or a pin under the workspaces root, it runs `workspace.sh delete` on it, never with `--discard`, and says the outcome on stderr (`close: deleted checkout <path>` or `close: kept checkout <path>: <reason>`). The stdout line `closed 1 session on <tty>` is unchanged and a refused delete never fails the close. `--keep-checkout` opts out. A rotation passes it: the replacement works in the same checkout, so a rotation deletes nothing. The orchestrator's own checkout is never under the root, so it is never touched.
- **The host's temporary directory, by `delete`.** The host keeps one directory per working directory a session ran in, named after that path with every character that is not a letter or a digit turned into `-`, holding the session's scratch (`ORCHESTRATOR_HOST_TMP`, else `/private/tmp/claude-<uid>`). The rule was first read as « every `/` », which held on the two entries checked; the host's directory for a path with a dot in it (`/srv/me/.cfg` gives `-srv-me--cfg`) showed the whole rule. One function, `encode`, spells it for `delete`, for the sweep's orphans and for the live-process guard. `delete` removes `<host tmp>/<encoded path>` after the checkout, when it exists and no live process uses it; a directory that stays is said. A session's working directory is never its host directory: that one is named after the directory the session STARTED in, while the session works there or below it. So a host directory is in use when its name is the encoding of a live process's working directory or of any ancestor of it (a session started in `<root>/p/c1/sub` and working in `sub/x` keeps `…-p-c1-sub`), or when a live process works inside it. An agent's scratch lives in its own host scratchpad, so it leaves with its checkout and the agent deletes nothing itself.
- **The leftovers, by `sweep`.** `workspace.sh sweep [--deadline <seconds>] [--dry-run]` decides each item under the root on facts, with one `gh pr list --state all` per repository (grouped by `origin`, never one call per checkout): a clone whose branch's pull request is merged or closed is deleted, provided the pull request is about the clone's own commit (its head is the pull request's head, or behind it) and the branch is not a long-lived one (`main`, `master`, `develop`, `trunk`, or the repository's default), which a pull request from a fork can share by name; a pin whose recorded pull request (`pin --pr <n>`, a file `workspace-pr` in the worktree's own git dir) is merged or closed, or whose head on the pull request moved off the pinned commit, is deleted; a clone with no pull request, a pin with no record, anything dirty, unpushed or in use is kept, with its reason. A host temporary directory whose name starts with the encoded root, `-`, the encoding of a project directory that exists under the root, and `-`, and matches no directory that still exists under the root (a checkout, or a project's own) and no live process (by the guard above), is removed: the orphans of checkouts deleted before this change. The encoded root followed by `-` alone is not enough: it is also the name of a sibling of the root, `<root>-old/x` or `<root>_2/x`. `--deadline` stops between items, `--dry-run` deletes nothing and says `would delete`, and `gh` unreachable or unauthenticated deletes nothing for that repository and says so once. Each line is `deleted <path>` or `kept <path>: <reason>`.
- **The sweep runs by itself.** The stop gate, for an `Orch :` session only, runs it once its checks have let the stop pass, never after a refusal (the host reads the decision at the hook's exit, and a refusal must not wait on a sweep), with what is left of its deadline minus a margin, at most once per ten minutes (a stamp file in the state directory). Each deletion is a line of the module's log; a sweep that fails or overruns is logged, killed inside the deadline, and never refuses a stop. No daemon, no background process, no launch agent: the sweep runs inside the calls named here.

The safety rule over all of it: never a dirty tree, unpushed commits, a pin whose head is on no branch of its source, or a directory a live process has as its working directory. Unpushed means a commit no remote branch holds, on a branch or on a detached head, or a stash: the branches alone see neither. The process table is read once per run with `lsof`, bounded, and a table that cannot be read refuses every deletion instead of reading as empty; a checkout git cannot read is refused the same way, with git's own first line, never read as clean and pushed. Every refusal is printed with its reason and is not an error of the caller; every deletion is printed and proved by the path's absence. A removal first moves its directory, in one rename, into a trash beside it (`<root>/.trash/` for a checkout or a pin, `<host tmp>/.workspace-trash/` for a host directory, each on the filesystem of what it takes), then removes it there: a removal killed half way leaves its remains in the trash, never a partial checkout at its path that would read as dirty for ever, and the sweep empties the trashes before anything else. A pin's source is told through `git worktree remove` of the path once it is gone. The trashes are dot directories, so `list` and the sweep's loops never read them as a checkout or an orphan. `--discard` stays the operator's word over every guard on the checkout itself, and never over the live-process guard on a host directory.

The first real dry run showed why the name alone is not enough: a clone on `main` read as « the pull request of branch main is merged », a fork's own `main` having been merged once. Two corrections came with the test of it, and one with that dry run. The pin guard « head on no branch » never fired, because `git branch --contains` lists the detached head itself and its output is never empty; it asks the refs now. And `gh pr list` lists thirty pull requests by default, so a merged one older than that read as « no pull request » and would never have been swept.

The review of the delivery measured the sweep starving inside the stop gate: with fifteen seconds it deleted nothing and never reached the orphans, the full dry run taking twenty-nine, most of it a list of a thousand pull requests per repository, and every run restarting from the first item with nothing known. So the order is the trashes, then the orphans (local and cheap), then the checkouts; each repository's list is cached in the state directory (`ORCHESTRATOR_STATE_DIR`, the stop gate's own resolution; a file per origin) for thirty minutes, and a failed or cut call is never written; and the list asks for two hundred, a merged pull request past them reading as « no pull request », which keeps the checkout: the safe side.

What the suite reads, on temporary repositories with a fake `gh` and a host temporary area of its own, never the real ones: each deliverable's behaviour, and each refusal (dirty, unpushed, a pin head on no branch, a live process inside, a process table or `gh` that cannot be read) seen to keep the directory, each check falling under its mutant. Left out on purpose: `create`, the push guard, the title guard of `close`, the stop gate's checks and messages, the context gate. The figure to read later is the count of deletable directories on the first real dry run, and the workspaces root's count after a week of use.

## 62. Nobody waits on CI in the foreground: one background watch per pull request

The cause, read from an audit of another orchestration (127 session transcripts, 2026-10-02 11:00 to 2026-10-03 18:45; the audit's figures, not re-measured here): 26 % of all session-minutes (1 507 of 5 811) went to CI polling loops, `for i in $(seq 1 120); do gh pr view N --json state,mergeStateStatus; gh pr checks N; sleep …` run until MERGED — 714 minutes by the orchestrator, 563 by its agents (37 % of their time); the five longest single waits were 67, 62, 58, 49 and 29 minutes; four agents crossed the context gate while waiting and were rotated.

What the plugin said that produced it: the agent's delivery clause watched the checks in the foreground after every push (`templates/agent-phase-brief.md`, `references/briefs.md`), under the standing rule that every command runs synchronously; the orchestrator re-read the checks at each idle notice; and the stop gate's refusal told it to « wait for the end in one call ». Each was reasonable alone; together they made waiting the default activity, and a session that waits in the foreground holds its context and its turn for nothing.

The mechanism it uses instead: a command started with the host's `run_in_background` keeps running after the turn ends and re-invokes the session when it exits. A background command that exits on the event costs no token while it waits.

- **`ci-watch.sh <pr> [--repo <owner/repo>] [--interval <s>]`** is the one way to wait. It reads the head once, waits (bounded, 180 s, `CI_WATCH_REGISTER_WAIT`) for checks to be registered on it — a push is seen before its checks, and « no checks reported » right then is not a red — then runs `gh pr checks --watch --fail-fast` with its output in a log file under the state directory, never on stdout, and writes beside that log its owner file (`<log>.session`, one line: the arming session's `CLAUDE_CODE_SESSION_ID`, or the file an earlier watch left is removed when no session armed this one; a write that fails is `unread`), the key the stop gate reads its watches by; then reads the pull request once more when that returns. That watch ends once the checks it knows are done, and a slower workflow's checks may not be registered yet, so before any green every workflow run of the head is read (`gh run list --commit <head>`), each unfinished one watched to its end, and the checks watched again, until none is unfinished — the bound, `CI_WATCH_REGISTER_WAIT`, restarting at each run watched — it bounds how long a run already watched may stay listed unfinished (the listing's lag), not how long a run may take — and a run still listed unfinished past it `unread`. One line and a code: `green` 0 (every workflow run of the head completed and every check passed, one at least), `red <names>` 1 — a cancelled check is red, though `--watch` exits 0 over it, so the buckets are read once before any green — `no-checks` 2 (none registered, or `skipped=<n>`: every check done and none passed), `moved <old> <new>` 3, `closed <MERGED|CLOSED>` 4, `unread <reason>` 5. It never loops on `gh pr view`. A draft guard is recognised by its job testing the draft flag in its own definition (`draft_guard.py`) and ignored while the pull request is a draft: on a draft the watch runs without `--fail-fast` (it would stop on the guard before the real checks finish), then classifies the failing names, `green` when every one is a guard and `red` naming only the others; `ignored-checks` remains the manual fallback of the stop gate. On another project a draft's every real job depended on its guard, so all of them were skipped, and the watch said `green` with nothing run: a green now needs one passing check, and a head whose checks were each skipped or a guard says `no-checks <pr> <head> skipped=<n>`, which the orchestrator reads as it reads no checks, ready on the suite's evidence. On a draft settled on its guards the green asks more: a check that depends on no guard (a secret scanner, say) passes whether or not any real job ran, so only a passed check whose job lists a guard in its `needs` counts (`draft_guard.py --dependents`); with none, the line is `no-checks <pr> <head> skipped=<n>`.
- **The orchestrator arms it**, once per pull request, when one it owns is opened or its head moves (`skills/orchestrator/references/review.md`, « Checks, in one background watch »): green is nothing in a project whose method opts into auto-merge and « ready » otherwise; a red outside what the pull request touches is re-run once (failed jobs) and the watch re-armed; a second red, or a red in what it touches, is reported and corrected; moved re-arms; closed stops the work; unread re-arms once, then reports. Never a foreground watch, never a loop, never a wait for MERGED outside the watch.
- **An agent's delivery ends at the push**: the suite green locally on the final head, the pull request opened, the final report, the stand-down. The watch clause is gone from the agent's duties. A red found later is the orchestrator's.
- **The stop gate** stops asking for a foreground wait (section 3, check 2). **The lint** refuses, in an implementer brief, a `gh pr checks --watch`, a `gh pr view` or `gh pr checks` in a loop around a sleep, and a wait « until merged »; check 7's background rule excepts `ci-watch.sh` outside an implementer brief.
- **Rotation**: an agent whose remaining work is waiting on CI is stood down, never rotated, and no session is spawned to watch CI.

**A merge is not the end of the watch.** On another project the base branch's push run went red after a merge — a flaky test, green on the pull request's merge ref — and stayed red fourteen hours unseen, because the watch exited on MERGED and nothing read the run of the merged commit. The watch used to exit on green, before any merge, so the follow-up below would never fire in the normal flow: two paths reach it. On green with auto-merge enabled (`autoMergeRequest` set), the watch does not exit; it reads the pull request again at its interval, bounded (1 800 s, `CI_WATCH_MERGE_WAIT`, inside the host's background bound), until it merges — then follows the base branch — or moves (`moved`, 3), closes (`closed`, 4), or neither within the bound, auto-merge disabled included (`green`, 0). After a merge by hand, the orchestrator's or the operator's, the orchestrator starts `ci-watch.sh <n>` again in the background, and it enters on MERGED. So a pull request found merged, at either read, is followed onto its base branch: `ci-watch.sh` reads the merge commit and the base branch (`gh pr view --json mergeCommit,baseRefName`), waits, bounded (600 s, `CI_WATCH_BASE_WAIT`), for the push runs on that branch at that commit, watches each to its end (`gh run watch --exit-status`, its output in the log file), and lists them once more when they end so a run registered late is watched too. A run cancelled there is no red — the branch's concurrency cancels it for a newer push, and `gh run watch --exit-status` exits 1 on any conclusion other than success — so the newest push run of the same workflow on that branch is followed instead and reported with its own sha; a cancelled run with no newer one is a red. Three lines: `base-green <sha>` 0, `base-red <sha> <run id> <failing job names>` 6, `base-no-run <sha> filtered=<n>` 7 when no push run came within the bound, `n` counting the push runs on that commit the workflow filter left out — above 0, a misnamed workflow, reported to the operator. The workflows followed are every push run on that commit unless named (`--base-workflow <name>`, repeatable, or `CI_WATCH_BASE_WORKFLOWS`, comma-separated), for a project whose slower suite should not hold the watch; `--no-base` keeps the former `closed <pr> MERGED`, 4, and a pull request closed without merge still ends on `closed <pr> CLOSED`, 4. The orchestrator reads base-red as it reads a red: a flake or an infrastructure fault re-run once, any other red or a second one reported and fixed at once in its own pull request — a red base branch is never left standing. The suite reads each line with the fake `gh`, the late run, the workflow filter, `--no-base` and the closed case, each seen to fall under its mutant.

What `gh` 2.100.0 returns, read with `gh pr checks --watch --fail-fast`: on a pull request whose checks all passed, exit 0 (measured on a merged pull request of this repository). The other states were not measured, for lack of a pull request in that state to read without creating one; the documented codes are 8 for pending checks and a non-zero code for a failure, and `gh pr checks` with no check registered prints « no checks reported on the '<branch>' branch » on stderr (the stop gate already tolerates that line). The script does not depend on the watch's own code beyond zero: it reads the failing names itself when the watch is not green.

What the suite reads: one case per exit code with a fake `gh`, the watch's output kept off stdout, the registration wait, the stop gate with and without a live watch and with a red, and the lint on each shape. Four mutants, each seen to fall: the watch's output on stdout, the registration wait removed, the stop gate ignoring a live watch, the lint missing `--watch`. The figure to read at the next audit: the CI-wait share of session time, 26 % to under 5 %.

## 63. An agent's report to the orchestrator is capped

The operator's ruling, after a trial: successions cost too much, and an orchestrator's context grows after its takeover mostly by the reports it reads. Uncapped reports measured 1,700 to 9,500 characters each, review reports the longest. A trial on three running orchestrations capped them; per one orchestration's report, 4 capped reports of 260 to 960 characters against 1,700 to 2,300 before, no follow-up question needed, nothing the artifact showed missing from them, and the « wrong or doubtful » line surfaced two points the orchestrator would not have seen. The implementer, rotation and comments briefs therefore cap every report at 12 lines / 1,000 characters — status, pull request number, head SHA, the suite's exit code and counts, the agent's `context_tokens`, deviations from the brief, and anything wrong or doubtful, a line never cut to fit the cap — with details in the pull request body or a file of the repository's, cited by path, and intermediate messages at 3 lines. The review brief leaves its findings uncapped in number, since they are the report's substance and the orchestrator verifies each, but writes each on one line of at most 200 characters; the rest of its report is capped at 1,000 characters, the « wrong or doubtful » line excepted, and the `norms-check:` machine line still closes it. A correction round settled three terms: the `context_tokens` field and the gauge line both put the context in the final report, as well as near the gate and when asked; the comments agent's per-thread assessments are exempt from the 3-line cap, sent in full with the reviewer's words since the orchestrator renders them to the operator item by item, and its end report carries the threads and their outcomes; and each review finding still ends with its proposed fix, as the review reference orders.

## 64. Done is measured against the spec's goals

A build was declared done against its plan while its spec's goals 3 to 5 were not reached: the plan's « after the build » section had moved them out of the work, no dispatch-record row was opened for them, and the stop gate saw nothing open. The same plan told the orchestrator to bind the tiers in `models.json`, against the routing skill's rule that the map is the operator's, and the directive won over the rule. Prose lost both times, so both became facts a module reads.

The spec's goals live once, in `goals.md` beside the build's dispatch record, kept by `dispatch-record.sh goals <record> init|status|plan|met|rule-out|reopen|check` over one stdlib script, `skills/orchestrator/scripts/goals.py`, the grammar's only implementation. `init` copies the numbered items under the spec's `## Goals` verbatim, with the aim; `--spec none` serves a build with no spec. Each row is `open`, `met` with evidence a local read verifies (a path that exists, a `commit:<sha>` git resolves; `pr:#n` and `run:<cmd>` only beside one of those, since a stop reads no network) or `ruled-out` with the operator's words. `open` refuses while no `goals.md` sits beside the record and warns on every open goal no phase carries (`unplanned=`), so a deferral « after the build » shows at every dispatch. The stop gate's done branch runs `goals.py check --json` on the `goals.md` beside each registered record and refuses `waiting: done` while a goal is open, a `met` row's evidence is not on disk, a ruling lacks his words, or the rows are not the spec's list one for one; with every goal holding, the first done over a new content of the files shows him the table once, because whether evidence that exists is enough is his judgment, not the gate's. A record with no `goals.md` (opened before it existed), a check that fails or runs out of time, and a moved spec pass and are logged; a declared block, a hand-over and a re-fired stop release before the check, as for the rows. The successor reads the goals by command at takeover and carries their line in its announcement, `/orchestrator:progress` opens with it, and a decision round asks every `unplanned=` goal.

The tier map's guard (`hooks/models-guard.ts`, mounted in `hooks/guards.ts` before the push guard) denies a session of the orchestration — one whose name gives it a role — a `Write`, `Edit` or `MultiEdit` of `<state dir>/models.json`, and a Bash line that writes it (a redirection, `tee`, `sed -i`, or `mv`/`cp`/`install`/`ln` with it as the destination); a project's own `models.json` passes unless the line names the state directory. The guard stands aside while the last prompt the operator typed in that session (at the terminal or through the bridge, never a peer's delivery) names `models.json` or a tier, so a binding he asks for is never a third lock. It denies rather than asks: under auto mode an ask goes to the mode's decider, not to him.

## 65. A launched session is given a lean tool set, chosen per spawn

The host sends the schema of every loaded tool on every call. A probe of the launcher on a read-only task measured 52,243 tokens on the first call, and 32,814 once eight tools and two settings were removed, for the same answer: 19,429 tokens per call, at 0.2215 token per character of schema. Five of the tools (`Artifact`, `SendFeedback`, `Workflow`, `ScheduleWakeup`, `ReportFindings`) have hardly been called by a session of this method, `Artifact` by 23 sessions in 556 and `ScheduleWakeup` once. The module registers three more in every session, `move_send`, `move_probe` and `end_session`, and only a session that moves an orchestrator between machines calls them: an orchestrator, or the coordinator that orders the move.

The operator's rulings (2026-10-18): remove from every session the launcher opens the tools no session calls; let the coordinator choose the tools with which it opens an orchestrator or an agent, and an orchestrator those of an agent, so that no session carries every tool; and let the caller know which tools exist on the machine. So the launch passes `--disallowedTools` with the default set of the title's role (`Orch :` and `Coord :` keep the three that move; every other title loses them too), placed before the strict flag and the server file, because the option takes several values and a prompt following it would be read as one more name. `--keep-tool <name>` takes a name out of the set and `--drop-tool <name>` adds any tool name or permission pattern; both repeat, every path that builds a launch honours them (plain, `--successor`, `--wake`, `--open`, `--auditor`, `--coordinator-successor`, `rotate`, which forwards what it is given and does not inherit the original's set), and an empty name or one name on both is refused before a tab exists. `Artifact` is removed by name and never by the host's `enableArtifact` setting: that setting also drops the « Scratchpad directory » line from the session's environment, which every agent brief relies on. The command `tools` prints what a session is given and what each item costs, one `kind | name | characters | tokens | roles` row per item, from the caller's own transcript or one named by `--transcript`; a name the default removes is listed even when the transcript lacks it, with `?`.

The same launch cuts what the host adds on its own, in the `--settings` it already passes. Every launched session loses the `<total_tokens>` reminder (`CLAUDE_CODE_TOTAL_TOKENS_REMINDER` set to `off`; its figure counts down from a budget unrelated to the gate the module measures) and the account's synced skills (`syncClaudeAiSkills` set to false, which hides them for that invocation and moves nothing on disk, where the same key in the user's settings would trash the synced directory); `--keep-synced-skills` keeps them. An `Agent :` session also loses the away recap (`awaySummaryEnabled` false) and the silent-turn reminder (`CLAUDE_CODE_SILENT_TURN_REMINDER` set to 0): an agent is read by its orchestrator alone. An orchestrator, an auditor and the coordinator are read by the operator, who keeps both. Two of these keys are internal to the host and undocumented, so each cut was proved by a probe on the version that ships with it, a cut that failed its probe was left out, and a launcher test keeps the keys passed; the probe is redone when the host's version changes.

The probes, their transcripts and figures are in the pull request that introduced this section.
